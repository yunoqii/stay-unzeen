# Режим Now: аудит дополнительных утечек

Дата: 2026-10-12 (день 5). Аналитик. Основа: ARCHITECTURE.md «Режим исполнения», API.md v0.4, RELAYER.md v2, review-day4 (D2, D14), review-day2 (H8). Код смотрел в рабочем дереве (незакоммиченные core/, web/), Now на беке ещё не реализован.

## TL;DR

1. Если сделать Now правильно, он почти ничего не добавляет сверх принятого компромисса «сеть видит, что время запроса ≈ время сделки». Ни Jito, ни priority fee не связывают Now-сделки друг с другом и с пулом сильнее, чем уже связывают публичные vault. Курс 1Click уже берётся из фонового кэша (D14 закрыт, `core/api/src/rate.rs:80-127`).
2. Есть три реальных выхода за рамки компромисса, и все закрываются в спецификации:
   - **Now на выводах (high).** `withdraw_token` за 1–3 с после покупки связывает сделку с адресом получателя **прямо в блокчейне**, без всякой сетевой слежки. Сетевой наблюдатель вдобавок получает IP ↔ кошелёк.
   - **Отпечаток Now на цепочке (medium).** Priority fee или Jito tip только у Now-сделок позволяют наблюдателю отделить Now от Delayed и вычесть Now-пользователей из пачки Delayed.
   - **Опрос статуса на фронте (high, было и до Now).** Опрос останавливается в момент исполнения, и это выдаёт время сделки или вывода сетевому наблюдателю в **любом** режиме. Delayed и Max privacy от сетевого наблюдателя по факту не защищают.
3. Два несоответствия сорвут демо или обесценят Delayed. Фронт шлёт `exec`, а core принимает только `privacy` с `deny_unknown_fields`, значит любое действие получит 400. Релейер берёт задания `LIMIT 1 ORDER BY not_before` без случайного порядка, поэтому порядок внутри пачки совпадает с порядком запросов.

## Находки

Формат: **серьёзность · где · проблема → исправление**.

### HIGH

**N-1 · `web/lib/api/mock.ts:521`, `web/components/portfolio/withdraw-panel.tsx:161,359`, `web/lib/exec.ts:24-28`, ARCHITECTURE.md:49 («buy/sell/withdraw») · Now на выводах связывает сделку и получателя прямо в блокчейне.**
Сценарий: Now-покупка M на vault V в T, затем Now-вывод M с того же V (D4: позиция по mint на одном vault) на свежий адрес в T+10 с, сумма ≈ покупке. Наблюдателю блокчейна этого достаточно: «V купил X в T» → «V отправил ≈X на A в T+10 с» → A купил. Сеть тут не нужна, это не тот компромисс, который принял владелец. Сетевой наблюдатель вдобавок получает IP ↔ A, то есть связь с реальным кошельком (который потом пойдёт на биржу), а не просто со сделкой. Умный вывод с Now отправит все части сразу, и разбиение ничего не даст. Профиль по умолчанию общий (`useDefaultExec`): у юзера с дефолтом Now выводы тоже пойдут Now. Подсказка «on-chain private» для вывода не соответствует действительности.
→ Now разрешить **только для buy/sell** (и create, если нужно). Для `withdraw_token`/`withdraw_zec` core отвечает 400 на `exec:"now"`. В UI вывода переключатель Now/Delayed не показывать: только «Standard / Max privacy» с текущими задержками. Профиль по умолчанию на вывод не распространять.

**N-2 · `web/lib/activity.ts:67-92` · Опрос статуса останавливается в момент исполнения и выдаёт время сделки или вывода в любом режиме (было и до Now).**
`poll()` шлёт `GET /api/actions/:id` раз в 2 с (после 60 с — раз в 6 с), пока `status === "queued"`, и прекращает, как только пришёл `sent`/`executed`. Провайдер VPS или ISP видит: IP X опрашивал сервер раз в 6 с с T0 и замолчал в T1. На Solana в T1−(0..6 с) перевод vault → A. Для `withdraw_token`, где каждая часть исполняется в своё случайное время, это прямая связь IP ↔ адрес получателя, и задержка 30 с–5 мин / 10–60 мин теряет смысл. Для Delayed-сделок опрос привязывает IP к конкретной пачке (это и так известно по времени POST), а размер ответа `queued` против `executed` (fill, rate, solanaTx) различим. Тем самым Delayed не даёт против сетевого наблюдателя того, что обещает README. Now здесь ничего не ухудшает, но без исправления текст «Delayed защищает от тайминга» нечестен.
→ Отдельный опрос по действию убрать. Статус действий отдавать в составе постоянного опроса портфеля (уже 10–15 с, независимо от состояния): `GET /api/portfolio` возвращает `actions[]` последних 24 ч. Ответ дополнять паддингом до фиксированного бакета (например, 4 КиБ). Если отдельный опрос оставляем: фиксированный интервал 10–15 с с джиттером, продолжать ещё случайные 1–5 мин после финального статуса, ответ паддить. Для Now пусть опрашивает быстро: там время и так раскрыто.

**N-3 · `core/api/src/actions.rs:15-16,25-62` против `web/lib/api/types.ts` (diff), ARCHITECTURE.md:49, API.md:7 · Контракт расходится: фронт шлёт `exec`, core принимает `privacy: "fast"|"max"` с `deny_unknown_fields`.**
На реальном беке любое buy/sell/withdraw с фронта получит `400`, то есть сорвётся демо. Хуже, если кто-то «починит» это маппингом `now → fast`: в коде `fast` означает эпохи 30–60 с, то есть Delayed. Пользователь выбрал Now, получил Delayed, ничего страшного. Обратное, `delayed → now`, будет утечкой.
→ Сначала API.md: `exec?: "now" | "delayed" | "max"` (по умолчанию `"delayed"`) **только** в buy/sell/create. `privacy` оставить для выводов (`"standard" | "max"`) либо переименовать, но тоже без `now`. Затем core: `enum Exec { Now, Delayed, Max }` с `#[serde(rename_all="lowercase")]`, `Delayed` по умолчанию, и тест «`exec:"now"` в withdraw → 400». Неизвестное значение → 400, без молчаливого фолбэка.

**N-4 · `adapters/src/relayer/postgres-queue.ts:76-85` · Пачка исполняется в порядке поступления (D2 закрыт только в core).**
Core ставит заданиям одной эпохи одинаковый `not_before` (`actions.rs:149-200`), но релейер берёт по одному: `ORDER BY (status='queued'), not_before LIMIT 1`. Одинаковые `not_before` выдаются в физическом порядке строк, то есть по порядку INSERT, а значит по порядку POST. Наблюдатель на VPS видит k запросов и k сделок в том же порядке, и пачка не даёт ничего. Это прямо касается Now: Delayed — единственная защита от того, что Now сознательно не защищает. RELAYER.md §1 требует случайный порядок, код этого не делает.
→ Минимум: `ORDER BY (status = 'queued'), not_before, random() LIMIT 1`. Последовательные claim дают случайную перестановку внутри эпохи. Для Now — отдельная полоса (см. требования R-relayer-1).

### MEDIUM

**N-5 · Будущая реализация priority fee / Jito (`adapters/src/tx.ts:53-56`, `config.ts:39`) · Now-сделки отличимы на цепочке.**
Сейчас у всех tx один `SOLANA_PRIORITY_MICROLAMPORTS` (по умолчанию 0). Если добавить `setComputeUnitPrice` или tip **только** для Now, любой индексатор разметит каждую сделку пула как Now или Delayed. Сам по себе ярлык личность не раскрывает, но он:
- даёт сетевому наблюдателю уверенность («сделка в T+2 точно Now, значит это IP, приславший POST в T») вместо гипотезы;
- позволяет вычесть Now-пары «запрос–сделка» и сузить пачку Delayed до остальных запросов (см. N-7);
- делает вечным публичный признак «этот anon-набор торговал срочно».

Уникальное значение (например, ровно 123 457 µlamports или tip = сумме комиссии юзера) работает как отпечаток режима. Пул отпечатком не выдаётся: vault и так публичны.
→ Единый профиль комиссий для **всех** tx пула. Один и тот же квантованный compute unit price (из фонового кэша, см. N-6) у Now и Delayed, округлённый до ступеней (например, до 1 000 µlamports или степеней 2). Tip либо у всех tx пула, либо ни у одной. Пул платит priority fee за Delayed из спреда: на pump.fun это ~0,0000x SOL на сделку. Комиссия ускорения юзера — **плоская сумма в реестре**, никак не связанная с фактическим fee/tip конкретной tx (N-8). Не помечать Now никакими инструкциями (memo, отдельный ComputeBudget-порядок).
Остаток, который не убрать: Delayed-сделки идут кучкой на границе эпохи, Now — поодиночке между границами. При малом объёме большинство эпох содержат 0–1 сделку, поэтому одиночная сделка неоднозначна. Это в README.

**N-6 · Будущая реализация · Helius `getPriorityFeeEstimate` по требованию.**
Если вызывать оценку в момент Now-действия с сериализованной tx (так в документации Helius: передаётся `transaction`, проверено 12.10), Helius получает tx **до** отправки: vault, mint, сумму. Плюс в его логах вызовы оценки будут только перед Now-сделками, и это та же разметка Now/Delayed для третьей стороны. IP юзера Helius не видит, только IP сервера и API-ключ оператора. Если Helius одновременно ещё и RPC для отправки, он и так видит tx при `sendTransaction`, но вызов только перед Now-сделками всё равно добавляет ярлык.
→ Фоновый кэш, как у курса (D14). Раз в 10–20 с с джиттером, вне зависимости от запросов, `getPriorityFeeEstimate` с `accountKeys` = только программа площадки (pump.fun / DBC), без vault и mint, уровень `Medium`/`High`. Результат квантовать (N-5) и использовать для всех tx. Нет свежей оценки (> 60 с) — брать последнюю ×1,5, по требованию не дёргать. На devnet оценки Helius нет в документации (видел только mainnet-эндпоинт): там фиксированное значение.

**N-7 · Архитектура · Смешение режимов сужает anonymity set Delayed.**
Против сетевого наблюдателя у Delayed-пользователя защита равна k = числу Delayed-действий в его эпохе: POST-время однозначно задаёт эпоху, ведь граница — ближайшая следующая. Каждый, кто выбрал Now, уходит из пачки, и k падает пропорционально доле Now. Особенность хакатона: юзеров единицы, k часто = 1 уже без Now. Отличить по сети Now-запрос от Delayed-запроса наблюдатель может только по времени ответа сделки (и по размеру тела, N-9). На цепочке, если N-5 не исправлен, это можно сделать сразу.
→ (1) N-5 и N-9 обязательны. (2) Дефолт Delayed не менять. В UI Delayed показывать «сколько действий в текущей пачке» **не надо**: это тоже утечка. (3) Roadmap (не на 16 дней): cover-сделки пула в эпохах (ребаланс, мелкие buy/sell собственных позиций), чтобы k ≥ 2 всегда. (4) README честно: «защита Delayed растёт с объёмом; при единичных пользователях она слабая».

**N-8 · Будущая реализация реестра · Сумма комиссии ускорения как отпечаток.**
Если комиссию считать как фактический fee/tip конкретной tx (pass-through) и писать отдельной строкой `ledger_ops`, у этой строки рядом `anon_pubkey` и сумма, которая ровно равна публичному tip/fee tx. Это ещё одна связь anon-ключ ↔ подпись (как D1). Ненулевое `fee_zat` у buy/sell кроме того помечает действие как Now, и пока janitor его не обнулит, это видно любому, у кого есть БД.
→ Плоская комиссия из `PoolInfo.fees` (фронт уже ждёт `nowFeeLamports`, `web/lib/exec.ts:122`). В ZEC по курсу действия, включена в тот же hold, что и сделка, без отдельной операции журнала. Подпадает под D1-janitor (обнуление `fee_zat`/сумм через 24 ч, журналы удаляются через 48 ч). Сумма не должна зависеть от фактического fee. Разницу между плоской комиссией и фактом пул забирает или доплачивает сам. Комиссию **не вычитать из `lamports_in`**, иначе сумма сделки на цепочке перестанет подчиняться округлению D10.

**N-9 · `web/lib/exec.ts:52` (`withExec`) · Длина тела POST выдаёт режим.**
`"exec":"delayed"` на 4 байта длиннее `"now"`/`"max"`. TLS-запись длину тела не скрывает, и сетевой наблюдатель отличает Delayed от Now/Max. Max от Delayed (разные расписания эпох) — тоже, а это сразу сужает кандидатов до одной пачки. H8 (паддинг) ещё не сделан.
→ Паддинг тела `POST /api/actions` до фиксированного бакета (например, `pad` до 1 КиБ, 8 КиБ для create с картинкой отдельно). Core принимает и игнорирует `pad`. Подпись делать после паддинга, иначе ломается `deny_unknown_fields`, поэтому поле `pad` добавить в контракт. Дешевле: коды режимов одной длины (`"now"|"dly"|"max"`), но паддинг закрывает и разницу между buy и sell.

**N-10 · Сканер + UX · «Пополнил → сразу Now-купил» сужает до блока Zcash.**
Зачисление происходит в высоту B+K (K = 3), и это публично вычисляемо для любой Orchard-tx в блоке B. Orchard-транзакций в блоке мало, поэтому «Orchard-tx в B → Now-покупка через ~4 мин + реакция человека» коррелирует даже без сетевого наблюдателя. В Delayed то же самое плюс 30–60 с, разница небольшая, но Now её обостряет. Подсказка «Top up in advance» уже есть в FRONTEND.md:38.
→ Дёшево (core/scanner): случайная добавка 0–3 блока к моменту зачисления (`credit_at = B + K + rand(0..3)`). В UI при первом действии в течение 10 мин после зачисления показать мягкое предупреждение «Just topped up? Waiting a bit makes the deposit harder to match», без блокировки.

### LOW

**N-11 · Jito: что видят третьи стороны (если включать на mainnet).** Проверено по docs.jito.wtf 12.10.
- Block engine видит IP сервера, UUID (если используем `x-jito-auth`) и полную tx до попадания в блок. IP юзера не видит. Публичного мемпула Jito нет с 8.03.2024, searchers бандлы не получают. Jito заявляет, что бандлы явно не раскрывает, но при uncled-блоках (пропущенный слот) tx может быть ретранслирована кем угодно и исполнена без атомарности. Для одиночной Now-tx это не утечка приватности (tx и так станет публичной через секунды), а риск сэндвича.
- Tip: перевод SOL на один из 8 публичных tip-аккаунтов, они общие для всей сети Solana. Аккаунт tip ничего не связывает, если платит сам vault в той же tx (Jito так и рекомендует: tip в той же tx, не через ALT). **Нельзя** заводить отдельный «tip-кошелёк» пула. Он связал бы все Now-tx и creator-адреса между собой и превратил бы tip в маркер Now. Сумма tip — как N-5: квантованная, из фонового `tip_floor`, одинаковая у всех tx пула.
- Получатель tip (валидатор-лидер) видит то же, что и все: публичную tx.
- `sendTransaction` у Jito всегда `skip_preflight=true`. Рекомендуемый сплит 70 % priority fee / 30 % tip, минимум tip 1 000 лампортов, лимит 1 запрос/с на IP на регион без ключа. Devnet у Jito нет, есть только testnet (`testnet.block-engine.jito.wtf`). Значит, Now на devnet = только priority fee, и демо Jito-части возможно лишь на mainnet.
→ Рекомендация на 16 дней: **Now без Jito**. Хватит priority fee через RPC со stake-weighted QoS (Helius и т. п.): меньше третьих сторон, нет второго канала со своими логами, нет вопроса «tip только у Now». Jito оставить для fair-launch бандла, где он нужен по сути. Если Jito всё же будет: `bundleOnly=true` + аккаунт `jitodontfront…` (только read-only) у всех tx пула против сэндвича на покупках с проскальзыванием до 5 % (`SLIPPAGE_BPS`).

**N-12 · `exec_mode` в `relayer_jobs` (ARCHITECTURE.md:49) · Ярлык режима рядом с публичной подписью.**
У релейерской роли колонка видна, а `signature` хранится вечно. Утечка БД вместе с логами провайдера дадут «эта сделка была Now». Мелочь на фоне D1.
→ Огрублять в settle вместе с временами: `exec_mode = NULL` (или `'batched'`/`'now'` → NULL через 24 ч вместе с `action_id`). Релейер логирует `job.id, op, venue, status, duration` без режима, или режим без `job.id`.

**N-13 · `web/lib/exec.ts:56-110` · Настройка по умолчанию в localStorage открытым текстом (`unzeen.exec.<network>`).** На сервер не уходит. Это проверено: единственный выход — поле `exec` в теле действия (`withExec`), в URL, query, cookie и заголовках режима нет. Кто имеет доступ к устройству, видит предпочтение и, косвенно, факт использования Unzeen, но то же самое уже выдаёт `vault` в localStorage.
→ Оставить как есть. Опционально хранить внутри зашифрованного vault-блоба. Не добавлять режим в URL (`?exec=now`) и в аналитические события.

**N-14 · Курс 1Click (D14) · Проверено, закрыто.** `RateProvider::get()` только читает кэш (`core/api/src/rate.rs:80-101`), обновление идёт фоновым циклом раз в 30–60 с (`rate.rs:119-131`), других вызовов `refresh()` в `core/api/src` нет. Запрос к 1Click в момент Now-действия не уходит.
→ Требование на будущее: Now не должен «освежать» курс перед исполнением. При устаревшей котировке — спред ×2 или 503, как у всех режимов.

## Требования к реализации

### core (API, реестр)
- **R-core-1.** Контракт (сначала API.md): `exec?: "now"|"delayed"|"max"` только в buy/sell/create, по умолчанию `delayed`. В `withdraw_*` `now` → 400 `bad_request`. Неизвестное значение → 400.
- **R-core-2.** Now: `not_before = now()`, эпохи (`Epochs`) не трогать и не сдвигать. Расписание границ не должно зависеть от Now-запросов.
- **R-core-3.** Комиссия ускорения плоская (`PoolInfo.fees.nowFeeZat`, в ZEC, фронту для показа можно и лампорты), включена в hold действия, без отдельной строки `ledger_ops`, не вычитается из `lamports_in`. Округление D10 и срезка 0–1 % у Now те же.
- **R-core-4.** Janitor: `exec_mode`/`fee_zat` подпадают под D1-обнуление (24 ч), `exec_mode` в `relayer_jobs` → NULL при settle или вместе с `action_id`.
- **R-core-5.** Курс только из кэша (как сейчас). Никакого обновления по требованию для Now.
- **R-core-6.** Принимать поле `pad` (игнорировать) в `POST /api/actions`. Статусы действий отдавать в постоянном опросе портфеля с паддингом ответа (N-2).
- **R-core-7 (опц., дёшево).** Зачисление депозита в `B + K + rand(0..3)` (N-10).

### relayer (adapters)
- **R-relayer-1.** Две полосы: Now-задания (`exec_mode='now'`) берёт отдельный воркер сразу, не стоя за пачкой. Пачечные — с `ORDER BY …, not_before, random()` (N-4). Иначе Now будет ждать пачку, а сама пачка останется упорядоченной.
- **R-relayer-2.** Один профиль комиссий на все tx пула (buy/sell/create/transfer, Now и пачки): `setComputeUnitPrice` из фонового кэша оценки (10–20 с, `accountKeys` = только программа площадки), квантованный. Ни одной инструкции, отличающей Now.
- **R-relayer-3.** Без отдельного tip/fee-кошелька: fee и tip платит vault (или свежий creator для create) в той же tx.
- **R-relayer-4.** Jito на 16 дней не подключать для Now. Если подключать: tip у **всех** tx пула, квантованный из фонового `tip_floor`, в той же tx, случайный из 8 tip-аккаунтов, `jitodontfront` read-only. UUID не обязателен.

- **R-relayer-6.** Логи без `exec_mode` рядом с `job.id`/временем. Сломавшуюся Now-tx повторять по общим правилам (только увеличение `not_before`).

## Черновик для README (threat model)

> **Execution modes and timing.** Every trade is executed by a shared pool vault, so the chain never shows who traded. What remains is timing. In **Delayed** (default) actions wait for the next pool batch (every 30–60 s; 5–15 min in **Max privacy**) and run in random order, so someone watching the network can only narrow your request down to a batch. That protection is only as strong as the number of other people in the same batch, and while Unzeen's volume is small it is weak. **Now** executes in 1–3 s with a priority fee. On-chain it looks exactly like every other pool trade: same fee profile, no marker. But anyone who can see your connection (your ISP, Wi-Fi operator, VPN provider, or the hosting provider of our server) can match the moment you sent a request to the trade that follows it. Use Tor or a trusted VPN if that matters to you. Choosing Now also shrinks the batches that Delayed users hide in. Withdrawals are never instant: they always use a delay, because an instant withdrawal would link a trade to the receiving address on-chain, not just on the network. We never fetch prices or fee estimates at the moment of your action: the ZEC/SOL rate and fee levels are refreshed in the background on a fixed schedule.

(Строку «same fee profile, no marker» писать только после R-relayer-2. Строку про withdrawals — после R-core-1 / R-web-1.)
