# Спека: приватные лимитки / take-profit / stop-loss

Автор: analyst · Дата: **2026-10-12** · Основа: FEATURES (доп. 1), ARCHITECTURE (режимы исполнения), API.md v0.5 (черновые `order_create`/`order_cancel`/`Order`) и v0.6 в рабочем дереве, RELAYER.md v2, INTEL.md v1, review-day4 (D1, D2, D10), token-intel.md. Код не трогал. Правило: **любая утечка = дисквалификация**.

## Вывод (TL;DR)

1. **Ордер — запись только в реестре** (`orders`) с hold при создании (ZEC для покупки, токены для продажи). В момент срабатывания ордер превращается в обычное действие `buy`/`sell` в режиме **Delayed/Max**: эпоха, случайный порядок, округление D10. На цепочке такая сделка **неотличима** от ручной, а по таймингу она **лучше** ручной: в момент исполнения от пользователя нет HTTP-запроса, поэтому связки «IP → сделка» (D2) нет.
2. **Цена — только из тика индексатора** (45–75 с). Индексатор раз в тик читает пачкой кривые **всех** токенов пула, и это расписание не зависит от наличия ордеров. Core проверяет условия после каждого тика. Отдельных RPC-запросов «под ордер» нет: иначе провайдер RPC увидел бы, по каким mint стоят ордера. Ордера в MVP — только по mint, которыми торговал пул (`tokens`), площадка pump.fun (кривая).
3. **Манипуляция вредна только для SL** (продавить цену вниз и выкупить). Защита: подтверждение на двух тиках подряд, `slippageBps` от цены триггера (продавать на дне SL не будет), исполнение через 30–60 с после триггера. TP и лимитная покупка при манипуляции исполняются по *лучшей* для пользователя цене. Ретеншн как D1: суммы и триггер закрытого ордера стираются через 24 ч, строка удаляется через 48 ч. Объём: backend ~1,75 дня, frontend ~1,25 дня.

## 1. Типы и семантика

| `kind` | Условие (цена `p` из тика, SOL за 1 целый токен) | Сторона | `amount` | Hold |
|---|---|---|---|---|
| `limit_buy` | `p ≤ trigger` | buy | зат (ZEC) | `amount` зат |
| `limit_sell` | `p ≥ trigger` | sell | базовые единицы токена | `amount` токенов |
| `take_profit` | `p ≥ trigger` | sell | базовые единицы | `amount` токенов |
| `stop_loss` | `p ≤ trigger` **на 2 тиках подряд** | sell | базовые единицы | `amount` токенов |

- `take_profit` на сервере **то же самое**, что `limit_sell`. Отличается только в UI: TP задаётся «+X % от средней цены входа», и эта средняя считается **только в браузере** (FEATURES 7). На сервер уходит только абсолютный `triggerPriceSol`, средняя цена входа и PnL на сервер **никогда не отправляются**.
- `limit_buy` по цене выше текущей и `limit_sell` ниже текущей разрешены: сработают на ближайшем тике. По приватности это то же самое, что Delayed-сделка (§4).
- **Bracket (TP + SL одним hold)** — P2, вне MVP: `kind: "bracket"`, `tpPriceSol`, `slPriceSol`, одна блокировка токенов, первым срабатывает тот, чьё условие выполнилось раньше. Без него TP и SL на одну позицию не поставить: каждый держит свой hold. В MVP UI предлагает TP **или** SL на позицию либо делит позицию на две части.
- **Площадка:** MVP — только `pumpfun` (кривая). Токен ушёл в AMM → открытые ордера закрываются `failed: graduated`, hold освобождается. Meteora DBC — когда будет адаптер. Jupiter — нет.

### Поля ордера
| Поле | Смысл |
|---|---|
| `id` | 128 бит случайных, hex |
| `anon_pubkey` | владелец (только в core) |
| `venue`, `mint` | mint обязан быть в `tokens` (торговался пулом) |
| `kind` | см. таблицу |
| `trigger_price_sol` | `NUMERIC`, > 0, ≤ 18 значащих цифр |
| `amount`, `hold_zat` / `hold_tokens` | сумма и hold |
| `slippage_bps` | допуск от цены **триггера**: по умолчанию 500 для `limit_*`/TP и 1 500 для SL; диапазон 50–5 000 |
| `exec_mode` | `delayed` (по умолчанию) или `max`. **`now` запрещён:** при исполнении пользователя нет, а Now-полоса дала бы точное «время тика = время сделки» без выгоды |
| `expires_at` | TTL 1 ч – 72 ч, по умолчанию 24 ч, округлён **вверх до часа** |
| `status` | `open` → `triggered` → `filled` \| `failed`; `open` → `cancelled` \| `expired` |
| `attempts` | число срабатываний (повтор после `slippage`, максимум 3) |
| `sl_armed_at_tick` | для SL: тик, на котором условие выполнилось впервые |
| `action_id` | действие, созданное при срабатывании (обнуляется по D1) |
| `created_at` | округлено вниз до минуты; `closed_at` — до часа |

### Hold, отмена, срок жизни
- **Создание** (`order_create`): одна транзакция Postgres — nonce + hold (`UPDATE … WHERE available >= x`, как у действий) + `INSERT orders`. Проверки: `amount ≥ minActionZat` (для sell — оценка по цене тика ≥ `minActionZat`), лок создателя (`423 creator_locked`, если продажа затронет залоченные токены), `frozen` → `423 balance_frozen`, лимиты (§6).
- **Отмена** (`order_cancel`): только из `open`. Одна транзакция `SELECT … FOR UPDATE` + hold → available + `status='cancelled'`. Из `triggered` → `409 order_not_open` (сделка уже в эпохе, как у обычного действия отмены нет). Чужой или несуществующий → `404`.
- **Истечение**: janitor раз в 60 с; `expires_at < now()` и `open` → `expired`, hold освобождается. Срабатывание и истечение конкурируют через `FOR UPDATE SKIP LOCKED`.
- **Срабатывание** (§3): hold **переносится** с ордера на новое действие без изменения баланса. Повторный hold не берётся, двойного списания нет.
- **После settle** действия: `confirmed` → ордер `filled`. `failed: slippage` → если `attempts < 3` и ордер не истёк, ордер снова `open` (hold возвращается на ордер), иначе `failed` и hold освобождается. Другие ошибки (`graduated`, `pool_liquidity`, `creator_cap`) → `failed` сразу. Релейер уже делает preflight-симуляцию (`adapters/src/tx.ts:39-57,251`): tx со slippage не уходит в сеть, так что «серии неудачных продаж» в цепочке не будет.

## 2. Источник цены и частота

### Варианты
| Источник | Свежесть | Утечка | Вердикт |
|---|---|---|---|
| `tokens.price_sol` | обновляется только после сделок **пула** (RELAYER §5) | нет | не годится: цена стоит, пока пул не торгует |
| Котировка адаптера (`quote` → `getAccountInfo(curve)`) по ордеру | секунды | **да**: провайдер RPC видит опрос кривой M, только пока на M есть ордер, и его частоту | **запрещено** |
| Подписки индексатора (`accountSubscribe` для `hot`) | реальное время, но копятся до тика | `hot` = «сделка пула за час», от ордеров не зависит | частично: не-`hot` mint обновляются раз в 30 мин |
| **Новый «ценовой проход» индексатора**: на каждом тике `getMultipleAccounts` по PDA кривых **всех** закреплённых mint (`intel_warm.pinned`), ≤ 100 на вызов | тик, 45–75 с | нет: набор = все токены пула, от ордеров не зависит | **рекомендация** |

**Решение:**
- Индексатор (INTEL.md v2) на каждом тике читает кривые всех `pinned` mint (1 вызов на 100 mint; при десятках токенов пула это 1–2 вызова) и пишет в той же транзакции тика `intel_prices(mint PK, price_sol NUMERIC, status, as_of, prev_price_sol, prev_as_of)`. Для `hot` mint берётся последнее значение из подписки в памяти, если оно свежее. Формула pump.fun: `price = (virtual_sol_reserves / 1e9) / (virtual_token_reserves / 10^decimals)`.
- Ордера разрешены **только** для mint из `tokens` (они всегда `pinned`). Ордер на mint, найденный поиском, но не торговавшийся пулом, → `422 order_unsupported_mint`. Иначе пришлось бы держать его в warm set из-за ордера, а это видно RPC: mint продолжают опрашивать после того, как приманки того же тика истекли.
- Core не ходит в RPC. Оценщик ордеров запускается, когда в `intel_meta.last_tick_at` появилось новое значение (опрос раз в 1 с, тот же цикл, что settler).
- `intel_prices` — публичные рыночные данные. Можно отдавать и как `Token.priceSol` (свежее, чем сейчас), утечки нет.

### Манипуляция ценой
Кривая pump.fun тонкая. Атакующий может продать крупно, обвалить цену, дождаться продажи пула по SL и выкупить дешевле. Комиссия pump.fun туда-обратно ~2 %, при крупном SL это окупается.

| Тип | Кому вредит манипуляция | Защита |
|---|---|---|
| `stop_loss` | **пользователю**: продаёт на искусственном дне | (1) условие на **двух тиках подряд** (≥ 45 с удержания цены, цену за это время выкупают другие трейдеры); (2) `minOut = amount × trigger × (1 − slippageBps)`: если цену уронили ниже допуска, продажа не пройдёт preflight, ордер перевзводится (до 3 раз); (3) исполнение в эпоху через 30–60 с после тика, на эпохе цена уже другая |
| `take_profit` / `limit_sell` | атакующему: пул продаёт ему по завышенной цене | `minOut` от цены триггера; пользователь получает ≥ желаемого |
| `limit_buy` | атакующему: пул покупает у него по заниженной цене | `minOut` от цены триггера × (1 + slippage); пользователь покупает ≤ желаемого |

- **Время тика публично** (`retryAfterMs` из `intel_meta.next_tick_at`, INTEL.md), поэтому один тик можно «подгадать». Отсюда два тика для SL. Ещё дешевле — сэмплировать цену в случайный момент внутри тика, а не в его начале (вопрос 3).
- **Зондирование:** атакующий двигает цену ступенями и смотрит в ленте, когда «unzeen sold». Так он узнаёт, что у **пула** есть SL около уровня X. Это знание об агрегате пула, а не о человеке, к anon-ключу или Zcash-tx оно не ведёт. В README: «orders are hidden from the chain, but a pool-level stop can be discovered by probing the price; it never reveals who placed it».
- Честная оговорка для UI: «Stop-loss checks the price about once a minute and executes in the next batch. It is not a guaranteed exit in a crash.»

## 3. Исполнение (оценщик в core)

После нового тика, в одной транзакции Postgres:
1. `SELECT … FROM orders WHERE status='open' AND mint = ANY(<mint с новым intel_prices.as_of>) FOR UPDATE SKIP LOCKED`.
2. Для каждого ордера:
   - условие из §1; для SL — `sl_armed_at_tick` (первый тик ставит метку, второй подряд срабатывает; если условие сорвалось, метка сбрасывается);
   - `frozen` → пропуск (ордер ждёт); курс старше 120 с → пропуск (для buy);
   - `limit_buy` создателя → проверка капа (`creator_cap` → `failed`).
3. Срабатывание: `INSERT actions` (kind `buy`/`sell`, суммы, курс из кэша, D10-округление для buy) + `INSERT relayer_jobs` (`exec_mode = order.exec_mode`, `not_before` = ближайшая граница эпохи). Hold переносится с ордера на действие. `orders.status='triggered'`, `action_id`, `attempts+1`.
   - `buy`: `lamports_in` = ZEC-hold × курс, с срезкой и округлением D10; `min_out = floor(lamports_in / (trigger × (1 + slippage)) × 10^decimals)`.
   - `sell`: `token_amount = amount`; `min_out` (лампорты) = `amount / 10^decimals × trigger × (1 − slippage)`.
4. Обработка в случайном порядке внутри транзакции. Логи — только счётчики (`orders_triggered=N`), **без** mint, цены, id и времени ордера.

Релейер про ордера не знает ничего: для него это обычные `buy`/`sell` (RELAYER.md менять не нужно).

## 4. Приватность: почему ордер не хуже обычной сделки

| Канал | Ручная сделка Delayed | Ордер |
|---|---|---|
| Цепочка Solana | vault пула, сумма (с D10), эпоха | **то же**: неотличимо, `FeedEvent.kind` остаётся `buy`/`sell`, без маркера «order/SL» |
| Сетевой наблюдатель (ISP, провайдер VPS) | POST за 30–60 с до сделки (D2) | POST `order_create` за часы до сделки, в момент исполнения запроса **нет** → **лучше** |
| Время исполнения | эпоха после запроса пользователя | эпоха после пересечения цены, которое определяет публичный рынок, а не пользователь |
| Связь «ордер сработал при цене X» с anon-ключом | — | только у оператора (реестр), как и любая сделка. Наблюдатель видит «пул продал после падения ниже X», а это нельзя связать ни с ключом, ни с Zcash-tx |
| Хранение у оператора | действие, D1 | **хуже**: открытый ордер — это намерение, хранится до 72 ч. Закрывается зашифрованным томом (N2) и TTL ≤ 72 ч |

Остаточные утечки (честно, в README):
- **Сумма продажи = сумма покупки.** TP или SL на всю позицию, купленную одной покупкой, продаёт ровно сумму из публичной tx покупки. Это так же, как у ручного «продать 100 %». В UI то же предупреждение, что при выводе (FEATURES): «same amount as a recent buy».
- **POST без последующей сделки.** Наблюдатель сети видит POST, после которого в ближайшую эпоху нет сделки. Значит, это не buy/sell, а ордер, отмена или вывод. Тело выровнено `pad` (v0.4), тип не виден. **Low.**
- **Пользователь сам рассказал «у меня SL на X».** Это социальное раскрытие, UI его не подсказывает.

## 5. Что видит наблюдатель

- **Solana:** ничего до срабатывания. После — обычную сделку vault пула в эпоху. Ордеров on-chain нет, охотиться не на что, кроме зондирования (§2).
- **API для всех:** ничего. Ни счётчика ордеров, ни стакана, ни «N open orders» в `PlatformStats`. **Не добавлять** публичную метрику ордеров, даже агрегат.
- **Владелец:** свои ордера в `Portfolio.orders` (подписанный ответ, выровнен до 4096 байт).
- **RPC-провайдер (Shyft):** одинаковый ценовой проход по всем токенам пула на каждом тике.

## 6. Лимиты (DoS и стоимость)

- Открытых ордеров на ключ: **10**, на ключ и mint: **4**. Сверх → `422 order_limit`.
- Глобально открытых: 1 000 (сверх → `503 venue_unavailable`). Не показывать, что лимит пула исчерпан другим текстом: это раскрыло бы активность.
- Создание и отмена входят в общий лимит подписанных действий (60/мин).
- Комиссии за ордер нет (спред пула при исполнении как у сделки).

## 7. Хранение (D1)

| Поле / строка | Срок |
|---|---|
| Открытый ордер целиком | пока `open`/`triggered` (≤ 72 ч + повторы) |
| `created_at` | округлён до минуты при вставке; `closed_at` — до часа |
| После закрытия + 24 ч | `amount=0`, `hold_*=0`, `trigger_price_sol=NULL`, `mint=NULL`, `slippage_bps=NULL`, `action_id=NULL` |
| После закрытия + 48 ч | `DELETE` |
| Действие, созданное ордером | существующие правила D1 (`actions`, `relayer_jobs`, `ledger_ops`/`token_ops` 48 ч) |
| `intel_prices` | только текущее и предыдущее значение (истории нет; свечи — из `trades`) |

Ордер в БД (mint, trigger, amount) в связке с будущей сделкой даёт точную связь. Поэтому важен TTL ≤ 72 ч, затирание и зашифрованный том.

Изменение существующего черновика `order_create` в `SignedAction`:


## 9. Находки и риски (по убыванию)

**HIGH**
- **O1 · Опрос цены «под ордер» через RPC раскрывает провайдеру, что на mint есть ордер, и момент, когда его проверяют.** Это утечка намерения третьей стороне. *Исправление:* только ценовой проход по всем токенам пула на тике (§2). Запрет `quote()` в оценщике закрепить в ревью и в тесте (оценщик не имеет RPC-клиента).
- **O2 · Отправка средней цены входа или PnL на сервер** ради «TP +50 %» хранила бы у оператора историю цен входа, то есть сделки. *Исправление:* процент → абсолютная цена считается в браузере (§1).
- **O3 · Ретеншн.** Закрытый ордер с mint, trigger и amount рядом с anon-ключом — та же вечная связь, что D1. *Исправление:* §7. Тест janitor обязателен.

**MEDIUM**
- **O4 · Охота за SL манипуляцией кривой.** *Исправление:* 2 тика, slippage от триггера, Delayed (§2). Плюс честный текст в UI.
- **O5 · Ордер на mint, известный только по поиску**, требовал бы держать его в warm set и выдавал бы это RPC. *Исправление:* только mint из `tokens` (§2).
- **O6 · Двойное расходование hold** (cancel и trigger одновременно, повтор после slippage). *Исправление:* перенос hold в одной транзакции с `FOR UPDATE`, тесты на гонку cancel/trigger/expire.
- **O7 · `exec: "now"` для ордеров** давал бы точную связку «момент тика ↔ сделка», а выгоды нет. *Исправление:* запрещено (400).

**LOW**
- **O8 · POST без сделки** выдаёт, что это не buy/sell (§4). Тело и так выровнено паддингом.
- **O9 · Логи оценщика** с mint, ценой или временем срабатывания. *Исправление:* только счётчики.
- **O10 · Публичная метрика ордеров** (в stats или на странице токена). *Исправление:* не добавлять никогда.

## Открытые вопросы для лида / владельца

1. **Ордера только по mint, которыми торговал пул** (O5) — подтверждаете? Лимитная покупка «нового» токена без предварительной сделки пула в MVP недоступна.
2. **TTL максимум 72 ч** (а не «бессрочно», как ожидают трейдеры) — ради хранения намерений ≤ 3 суток. Ок?
3. **Сэмплировать цену в случайный момент тика**, а не в начале? Время тика публично через `retryAfterMs`, и это удешевляет манипуляцию одного тика. Цена — +0,1 дня у индексатора.
4. **Место в плане.** По оценке бек ~1,75 и фронт ~1,25 дня. В текущем плане слотов под это нет (дни 9–12 заняты Meteora/Jupiter/fair-launch/NEAR), а ещё Verify (бек ~2). Предлагаю поставить ордера **после** Verify и **вместо** Jupiter, который и так первым в порядке урезания. Если не влезает — урезать до `limit_buy` + `stop_loss` (бек ~1,25).
5. Bracket (TP+SL одним hold) — нужен в демо? Судьям он понятнее, но это +0,5 дня.
