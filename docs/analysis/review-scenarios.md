## Вывод
Механика денег в порядке: savepoint, блокировка строки плана, атомарная постановка шага, идемпотентный nonce у fl_*/chat. Запечатывание тоже корректно.

Главный дефект: **P2 проверяется только статически**. Исполнитель не смотрит, когда реально прошла последняя сделка по mint. Поэтому вывод токенов можно поставить сразу за исполнением ордера, причём и ордера плана, и внешнего (через `own_result {orderId|actionId}`). Кроме того, несколько полов (P4, P6, P9) исполнитель применяет только к соседним шагам, и их обходят через `of:"balance"`, `repeat` и промежуточные блоки.

## Проверено и чисто
- **Двойное исполнение и гонки.** Каждый план идёт в своей транзакции: `FOR UPDATE SKIP LOCKED`, `scenarios_due ORDER BY random()`. `submit_in` стоит за `SAVEPOINT`, `insert_run` и `save` в той же транзакции, поэтому падение до COMMIT не оставляет ни действия, ни hold, ни сдвига курсора. Для `order_*`/`claim` то же через `*_in` и savepoint. `in_flight` закрывается только по `actions.status` (`queued/executed/failed`, других нет).
- **fl_*/chat.** Своя транзакция, nonce и hash = SHA256(K_scn‖tag‖id‖cursor‖runs‖attempt‖rep). При повторе после краша `chat_replay` и `is_replay` возвращают исходную квитанцию (хэш совпадает), второй публикации нет.
- **Отмена.** cancel, start и replaces берут строку `FOR UPDATE` с `anon_pubkey = $pk`, чужой план → 404. Отмена во время шага ждёт исполнителя. Уже поставленное действие доисполняется, ордера плана закрываются с возвратом hold. `own_result`/`order_cancel` по id фильтруются по pk.
- **Лимиты.** 3 на ключ и 500 на пул считаются под advisory-lock, `replaces` исключён из счёта. 12 шагов, 40 исполнений (с repeat/dca/swap), TTL 1 ч–72 ч (7 сут без выводов), `expires_at` округлён вверх до часа. При TTL план закрывается как `expired`. После простоя пачки нет: каждый шаг получает новый `next_at`.
- **Hold.** Берётся в момент шага атомарно в `submit_in`. `balance_frozen` — не ошибка: шаг ждёт 60 с.
- **Sealed.** ChaCha20-Poly1305, случайный 96-битный nonce, AAD = случайный `sealId`(16)‖u16(step). Подмена между планами и шагами ловится (тест есть). Ключ лежит вне БД, без ключа сервер не стартует при `UNZEEN_SCENARIOS=1`. Blob удаляется в той же транзакции, где шаг поставил задание, а также в `close_in` (cancel/expire/fail/done) и в janitor.
- **Ретеншн.** Через 24 ч `plan`/`state`/`error`/связи runs затираются, через 48 ч строки удаляются (CASCADE). `created_at` округляется до минуты, `closed_at` до часа (триггер).
- **Логи.** Только счётчики. `LedgerError::Db` несёт только SQLSTATE, без значений.
- **Сеть и RPC.** В исполнителе нет ни одного RPC и ни одного запроса к 1Click: `rate.get()` читает только кэш, тики и снимки берутся из БД. `check_safety` по неизвестному mint ставит его в ту же очередь `intel_requests`, что и поиск по CA (пачка с приманками в `indexer.ts`).
- **Полы, которые работают.** P1 (Now только на шаге 1 после `manual_start` и не внутри repeat; повтор buy/sell → delayed), P3 (U(10,40) мин после зачисления), P5 у dca (веса ±20 %, интервалы U), P6 внутри swap, P7, P8 (`{step: swap}` резолвится в `to`). P2 по всем путям графа (goto/skip/repeat) в статике, выводы внутри repeat запрещены. Обходы из `review-numeric-hood.md` п. 1–5 закрыты. П. 11 закрыт для buy/sell (см. п. 7 выше).
- **Тела запросов.** `scenario_create` ровно 16384 Б (сервер принимает pad ≤ 16384), с картинкой — обычные корзины, как у ручного create. `scenario_start`/`cancel` ровно 1024 Б, ответы паддятся до 1024. Опрос Portfolio с фиксированным ритмом 10–15 с от сценариев не зависит. `nextAt` вниз до минуты.
- **Фронт.** Черновики и имена хранятся в IndexedDB под AES-GCM history-ключом (AAD = сеть‖pubkey), в открытом localStorage ничего нет. Mint для «Automate» передаётся в памяти, не в URL. `features.fl` в билдере жёстко `false`.
- **Публичный бандл.** `pnpm build:public` зелёный (4/4): маркеров fl_* нет ни в одном чанке. Из scenario-кода в бандл попадает только префикс `"fl_"`, его нет в списке маркеров, и он ничего не раскрывает.
