# Спека: Verify (proof of liabilities + публичные vault + резерв ZEC)

Автор: analyst · Дата: **2026-10-12** · Основа: ARCHITECTURE «Verify»/«Модель доверия», FEATURES, API.md v0.5 (+ черновик v0.6 fair-launch в рабочем дереве), RELAYER.md v2, INTEL.md v1, review-day2 (C1), review-day4 (D1). Код не трогал. Правило: **любая утечка = дисквалификация**.

## Вывод (TL;DR)

1. **Обязательства — отдельное Merkle-sum дерево на каждый актив** (ZEC и каждый mint). Каждый баланс разбит на 2–4 случайных куска. Листья — `SHA-256` с тегом, pubkey, случайным `blind` и номером снимка, поэтому листья разных снимков не связать. Дерево добито нулевыми листьями до фиксированного размера (≥ 1024). Суммы округлены **вверх**. Число пользователей и чужие балансы не раскрываются. Доказательство пользователь получает подписанным GET (ответ выровнен паддингом) и проверяет в браузере (`@noble/hashes`).
2. **Активы.** SOL и токены на vault Solana **проверяемы**. Каждый vault подписывает снимок своим ключом, так что «чужие» адреса не подставить. **Резерв ZEC в shielded-пуле доказать без viewing key сейчас нельзя.** ZIP 311 — Draft, только Sapling, реализации нет; в librustzcash (проверено локально, `zcash_primitives 0.31.0-pre.1`, `orchard 0.16.0`) есть только `OutgoingCipherKey` для Sapling. Раскрытие отдельных нот выдаёт tx депозитов. Поэтому ZEC-резерв — **«attested by operator»**: подписанное заявление, округлённое вниз. На странице это сказано честно, ZK proof of reserves — в roadmap.
3. **Корень публикуется раз в сутки** в 00:00 UTC по фиксированному расписанию, с коротким «замораживанием» релейера ради согласованности. Корень подписан ключом оператора и **заякорен memo-tx на Solana**, иначе оператор может показать разным людям разные корни. Между снимками наблюдатель видит только суточную дельту агрегатов, округлённую до 0.001 ZEC. Объём: backend ~2 дня, frontend ~1,5 дня. MVP без якоря и без разбиения — ~1 + 1 день.

## 1. Модель угроз для Verify

| Кто | Что не должен узнать | Чем закрыто |
|---|---|---|
| Любой посетитель /verify | число пользователей, баланс любого пользователя, связь баланса с anon-ключом или сделкой, изменения баланса одного пользователя во времени | паддинг, разбиение, новые `blind` и снимок в листе, публикуются только корни и суммы деревьев |
| Пользователь со своим доказательством | чужие балансы (в Merkle-sum доказательстве видны суммы соседних поддеревьев) | разбиение на случайные куски, случайные позиции, нулевые листья-заглушки |
| Сетевой наблюдатель (ISP, провайдер VPS) | сколько у пользователя активов (по размеру ответа) | ответ `/api/verify/proof` выровнен паддингом до 16 КиБ |
| Оператор (нечестный) | — (он и так знает всё) | не должен суметь: подставить чужой vault (подпись vault), показать разным людям разные корни (якорь в Solana), занизить обязательство через отрицательный лист (суммы `u64`, узел коммитит обе суммы детей) |

**Никогда:** UFVK/IVK/OVK, txid депозитов, коммитменты или нуллифайеры нот пула, «аудитор с viewing key под NDA» (это тоже третья сторона, видящая все memo, а значит дисквалификация).

## 2. Дерево обязательств

### 2.1 Что входит в обязательство
Для каждого `anon_pubkey` и актива `a`:
- **ZEC:** `balances.available_zat + balances.held_zat`. В `held` входят hold действий, ордеров (orders.md) и заявок fair-launch (номинал). Замороженный баланс (`frozen`) тоже входит: это долг пула.
- **mint:** `token_balances.available + token_balances.held`.
- **creator fees (`claimable`)** — пока `[]`. Когда появятся, отдельное дерево `SOL` (лампорты).
- Нулевые обязательства не включаются.

### 2.2 Округление
Значение округляется **вверх** до гранулы `g`. Для солвентности это консервативно: обязательство не меньше реального.
- ZEC: `g = 100 000 зат` (0.001 ZEC).
- mint: `g = 10^decimals` (1 целый токен).
Пользователь проверяет условие «закоммичено ≥ мой баланс на момент снимка».

### 2.3 Разбиение и паддинг
- Округлённое значение `V` разбивается на `s` кусков, `s` случайно из {2, 3, 4}. Куски кратны `g`, суммируются в `V`, нулевые разрешены. Делить равномерно случайно: выбрать `s−1` точек разреза на `[0, V/g]`.
- Листья всех пользователей и все куски перемешиваются случайно (CSPRNG).
- Размер дерева: `N = max(1024, nextPow2(2 × число_кусков))`, один для всех деревьев снимка. Свободные места — листья-заглушки со значением 0 и случайным `pubkey`/`blind`. По хешу заглушка неотличима от настоящего листа. Сумма 0 видна, но таких листьев и так большинство.
- Наружу публикуются только `N` (одинаковый у всех деревьев) и корни. Число пользователей не видно. Бакет `N` растёт только при > 512 кусков; это грубая оценка, допустимо.

### 2.4 Хеши (SHA-256, байты big-endian)
```
leaf  = SHA256("unzeen/verify/v1/leaf" ‖ chainId[2] ‖ u32(snapshotId) ‖ asset[32] ‖ anonPubkey[32] ‖ u8(piece) ‖ u64(value) ‖ blind[32])
        asset: 32 нуля для ZEC, 32 байта mint (base58-декод) для токена, 32×0xFF для SOL (claimable)
        blind: 32 случайных байта, новые на каждый (снимок, ключ, актив, кусок)
dummy = тот же формат, anonPubkey и blind случайные, value = 0
node  = SHA256("unzeen/verify/v1/node" ‖ L.hash ‖ u128(L.sum) ‖ R.hash ‖ u128(R.sum)),  sum = L.sum + R.sum
root  = (hash, sum) корня
```
- Узел коммитит **обе** суммы детей, а не только итог. Это известная поправка к схеме Максвелла: иначе оператор может уменьшить итоговую сумму, подменив разбиение между детьми.
- Значения — `u64` и не могут быть отрицательными. Это закрывает атаку «отрицательный лист гасит долг».
- `snapshotId` и `blind` в листе делают листья разных снимков несвязываемыми, поэтому наблюдатель не может следить за одним листом во времени.
- `anonPubkey` в листе не даёт оператору выдать двум пользователям с одинаковым балансом один и тот же лист.
- Векторы: `core/testdata/verify-vectors.json` (лист, узел, путь из 3 уровней, корень). Генерирует backend, frontend сверяет байт в байт, как с `unz1`.

### 2.5 Корень снимка
```
rootsDigest = SHA256("unzeen/verify/v1/snapshot" ‖ chainId ‖ u32(snapshotId) ‖ u64(takenAtSec) ‖ u32(N)
                     ‖ для каждого актива в порядке asset[32] по возрастанию: asset ‖ rootHash ‖ u128(rootSum))
operatorSig = ed25519(operatorKey, rootsDigest)   // pubkey оператора — в README и захардкожен во фронте
```
Якорь: memo-tx на Solana (`MemoSq4gqABAXKb96qnH8TysNcWxMyWCqXgDLGmfcHr`) с публикующего адреса пула: `unzeen:verify:v1:<chainId>:<snapshotId>:<hex(rootsDigest)>`. Публикующий адрес — отдельный ключ, пополненный с vault (он и так часть пула). Стоимость — одна tx ≈ 5 000 лампортов плюс единый priority fee пула. Делает релейер, новая `op = 'anchor'` (RELAYER.md v3), core в Solana не ходит.

## 3. Как пользователь получает и проверяет доказательство

1. Фронт: кнопка «Verify my balance» на /verify. Автоопроса нет.
2. `GET /api/verify/proof` (подписанный, как `/api/portfolio`, pubkey только в заголовке) → `VerifyProof` за последний снимок. `?snapshot=<id>` — только последний или предыдущий: приватные данные хранятся 48 ч, §6.
3. Браузер:
   - пересчитывает лист из `(chainId, snapshotId, asset, свой pubkey, piece, value, blind)` и проходит путь до корня;
   - сравнивает с `roots[asset]` из публичного `GET /api/verify`;
   - проверяет `operatorSig` над `rootsDigest`, пересчитанным из публичного снимка;
   - показывает сумму своих кусков по каждому активу, отметку «≥ ваш баланс на <время снимка>» и ссылку на якорную tx в эксплорере (клик пользователя, `rel="noreferrer noopener"`).
4. «Download proof (JSON)» — файл на диск. **Не класть в localStorage**: доказательство содержит баланс. Независимый скрипт проверки (`scripts/verify-proof.mjs`, ~60 строк, без зависимостей кроме `@noble/hashes`) — в репо, для судей.
5. Баланс нулевой в момент снимка → `proofs: []`, тот же размер ответа.

Ответ выровнен паддингом до кратного **16 384 байт**: размер не выдаёт число активов. Больше 12 активов у ключа → отдаём ZEC и 11 случайных, флаг `truncated` (редкий случай, только владельцу).

## 4. Активы

### 4.1 Solana vault (проверяемо)
- Список: все vault, на которых пул держит что-либо (`relayer_vault_usage` ∪ `mint_vaults` ∪ конфиг), адреса creator, если на них копятся creator fees, и публикующий адрес.
- **Доказательство владения:** на каждом снимке каждый адрес подписывает своим ключом `utf8("unzeen/verify/v1/vault\n" + chainId + "\n" + snapshotId + "\n" + address)`. Браузер проверяет ed25519 (`@noble/curves`; Solana-адрес и есть ed25519 pubkey). Транзакции для этого не нужны. Подписывает релейер: ключи vault есть только у него.
- **Балансы:** читает релейер на одном `finalized` слоте `S` (`getMultipleAccounts` по vault и их ATA через **Shyft**, т. е. провайдера чтения; список vault публичный, утечки нет) и пишет в `verify_assets`. Фронт к RPC **не ходит** (правило FEATURES). Для независимой проверки — ссылки в эксплорер по клику и готовая команда `solana balance <addr>` / `spl-token accounts --owner <addr>` в «Verify it yourself».

### 4.2 Резерв ZEC (только заявлено оператором)
Что проверил (2026-10-12):
- **ZIP 311 «Zcash Payment Disclosures»** — статус **Draft**, покрывает только Sapling («TODO: Add support for Orchard»), reference implementation «TBD». К тому же доказывает факт *платежа*, а не непотраченный остаток.
- **librustzcash локально** (`~/.cargo/registry`: `zcash_primitives 0.31.0-pre.1`, `orchard 0.16.0`, `zcash_client_backend 0.25.0-pre.1`): реализации payment disclosure нет. В CHANGELOG только `OutgoingCipherKey` для Sapling с пометкой «eventually be used to implement Sapling payment disclosures». Для Ironwood ничего. **[не подтверждено]** наличие чего-то в непубличных ветках.
- ZIP 304 (подпись Sapling-адресом) доказывает контроль адреса, а не баланс. Для Ironwood не применим.

Почему не годятся «самодельные» раскрытия:
| Вариант | Что утечёт | Вердикт |
|---|---|---|
| Раскрыть открытия входящих нот (`cmx`, value) | `cmx` лежит в конкретной tx, значит раскрыта **tx депозита и её сумма** → депозит ↔ время ↔ сумма → связь с первой покупкой | **запрещено** (утечка) |
| Консолидировать в «резервную» ноту и раскрыть её (+ нуллифайер для проверки «не потрачена») | tx консолидации (число входов ≈ число депозитов), а при трате — какая tx является выплатой пула (время выплат) | не делать |
| Раз в сутки вывести резерв на t-адрес и вернуть | вся сумма и движение публичны, дельты = суммы депозитов и выводов | не делать |
| Дать viewing key аудитору | третья сторона видит все memo (anon_pubkey) | **запрещено** (C1) |

**Решение для MVP:** `zecReserve = { amountZat (округлено ВНИЗ до 0.01 ZEC), zcashHeight, operatorSig }`, подписано тем же ключом оператора, что и корни. Значение — подтверждённый (≥ K) spendable-баланс кошелька пула по `zcash_client_sqlite` на высоте снимка. На странице явная плашка «Attested, not proven» с объяснением выше.

**Солвентность по ZEC.** Пул держит долг пользователей в ZEC частично в ZEC, частично в SOL (ребаланс ZEC→SOL, выручка от продаж). Проверка:
`liabilities.ZEC ≤ attestedZec + spareSol × lamportsPerZecSell⁻¹`, где `spareSol = Σ SOL на vault − лампорты в заданиях queued/claimed/sent − резерв на газ`. Две полосы на графике: «proven» (SOL) и «attested» (ZEC). По каждому mint: `liabilities[mint] ≤ Σ vault[mint]`, **полностью проверяемо**.

**Roadmap (README):** ZK proof of reserves по Ironwood-нотам (Halo2-схема: Σ непотраченных нот пула ≥ X с доказательством непринадлежности нуллифайеров, без раскрытия нот), FROST t-of-n на кастодии.

## 5. Снимок: когда и как

### 5.1 Расписание
- Раз в сутки, **00:00 UTC** (фиксировано и публично, от действий пользователей не зависит). На devnet для демо — плюс ручной запуск оператором `core verify snapshot` (только devnet; на mainnet ручной запуск не нужен).
- Почему не чаще: каждая публикация раскрывает дельту агрегатов, §5.3.

### 5.2 Согласованность (иначе «ложная несостоятельность»)
Продажа исполнена на цепочке, но ещё не прошла settle: на vault токенов уже нет, а в реестре они ещё `held`. Обратный случай (купили, не засчитали) безопасен. Процедура:
1. core ставит `pool_meta.verify_freeze_until = now()+120 s`. Релейер перестаёт брать новые задания (обе полосы). Fair-launch-tx в окне снимка не ставить: окно `t(R)` сдвигается.
2. core ждёт, пока нет заданий `claimed`/`sent` и нет `confirmed` с `settled_at IS NULL` (settler работает раз в 1 с), и нет выплат ZEC в статусе «отправлена, < K». Не дождались за 90 с → снимок пропускается, повтор через 10 мин (не «чаще», а сдвиг).
3. Релейер пишет `verify_assets` на `finalized`-слоте `S` и подписи vault.
4. core в одной транзакции `REPEATABLE READ` читает `balances`/`token_balances`, строит деревья, пишет `verify_snapshots` (+ `zecReserve`), ставит задание `anchor`. Снимает freeze.
- Задержка заданий Now/Delayed на ≤ 2 мин раз в сутки в известное время. Утечки нет.

### 5.3 Что видит наблюдатель между снимками
- Суточную дельту `Σ ZEC-обязательств` (гранула 0.001 ZEC на лист) = депозиты − выводы − покупки + продажи − комиссии за сутки, и дельту по каждому mint (она ≈ дельта vault, и так публична).
- **Риск:** при одном активном пользователе за сутки дельта ZEC ≈ его чистый поток. Это не связывает его ни с Zcash-tx (депозиты shielded), ни с anon-ключом. Связь возможна, только если депозит шёл с публичного источника (`publicSource`): сумма и так видна в цепочке, Verify нового не добавляет. Оценка — **low**. Если лид хочет строже — публиковать раз в 7 дней (вопрос 2).
- Появление нового дерева mint = у пула есть обязательство по mint. Это уже видно по балансу vault.
- **Не публикуем:** число листьев с ненулевым значением, число пользователей, гистограммы, «сколько человек проверили своё доказательство».

## 6. Хранение (D1)

| Что | Где | Срок |
|---|---|---|
| `rootsDigest`, корни и суммы по активам, `N`, `takenAt` (минута), `solanaSlot`, `zcashHeight`, `operatorSig`, `zecReserve`, `anchorTx`, `verify_assets` (vault, суммы, подписи) | `verify_snapshots`, `verify_assets` | **вечно** (это публичная история) |

`verify_leaves` связывает ключ с балансом. Это та же информация, что уже лежит в `balances`, нового риска нет. Но по D1 это журнал, а журналы живут ≤ 48 ч. Пользователь, которому нужна история, скачивает JSON.

## 7. Страница /verify (что показывать)

1. **Шапка снимка:** `#id`, время UTC (минута), Solana slot, Zcash height, бейджи «Operator signature ✓» (проверено в браузере) и «Anchored on Solana ↗» (ссылка на tx). Селектор истории снимков.
2. **Solvency по активам:** таблица `asset | liabilities (root sum) | assets | coverage % | proof`. Для mint — «proven». Для ZEC — составная полоса proven (SOL) + attested (ZEC), с явной подписью.
3. **Your proof** (если загружен anon-ключ): кнопка → проверка в браузере → по каждому активу «committed ≥ X» и анимированный `MerkleTrace` (уже есть в `web/components/verify/merkle-trace.tsx`) на **реальном** пути + «Download proof». Без ключа — CTA «Load your key».
4. **Vaults:** адрес (сокращённый, копирование), «signed ✓» (ed25519 в браузере), SOL, токены. Ссылка в эксплорер по клику, с пометкой «opens a third-party site».
5. **ZEC reserve:** сумма, высота, подпись. Блок «Why this is attested, not proven» (3 предложения из §4.2) и roadmap.
6. **Verify it yourself:** скачать снимок JSON и команда `node verify-proof.mjs snapshot.json proof.json`.
7. **Что мы НЕ показываем и почему:** число пользователей, чужие балансы, viewing key. Судьи это ценят.

Фронт: проверка только локально, без сторонних запросов. Ничего из доказательства в localStorage. Текущий текст STEPS на /verify совместим, только «ZEC reserve must cover» → «ZEC reserve (attested) and SOL (proven) must cover».

## 8. Черновик API (для API.md v0.7, API.md не правил)

```ts
// GET /api/verify            → VerifySnapshot (последний), публичный, Cache-Control: public, max-age=300
// GET /api/verify/snapshots?before=<id>&limit=30 → VerifySnapshotSummary[] (история, новые первыми)
// GET /api/verify/:id        → VerifySnapshot | 404
// GET /api/verify/proof[?snapshot=<id>] (подписанный) → VerifyProof; только последний/предыдущий снимок, иначе 404
//   ответ выровнен полем pad до кратного 16384 байт; no-store

type AssetId = "ZEC" | "SOL" | string;     // string = base58 mint

interface VerifySnapshotSummary {
  id: number; takenAt: number;             // unix мс, округлено до минуты
  rootsDigest: string;                     // hex
  anchorTx?: string;                       // подпись Solana memo-tx; нет — ещё не подтверждена
}

interface VerifySnapshot extends VerifySnapshotSummary {
  chainId: string;                         // "0202" | "0101"
  leaves: number;                          // N, одинаков для всех деревьев
  solanaSlot: number; zcashHeight: number;
  operatorPubkey: string;                  // base58 ed25519 (фронт сверяет с захардкоженным)
  operatorSig: string;                     // base58, над rootsDigest
  trees: { asset: AssetId; decimals: number; root: string; sum: string }[];  // sum — базовые единицы (зат / токены / лампорты), целое
  vaults: {
    address: string; sig: string;          // ed25519 подпись "unzeen/verify/v1/vault\n<chainId>\n<id>\n<address>"
    lamports: string;
    tokens: { mint: string; amount: string }[];   // базовые единицы
  }[];
  committedLamports: string;               // SOL в заданиях queued/claimed/sent + резерв на газ (вычитается из покрытия ZEC)
  rateLamportsPerZecSell: string;          // курс, по которому SOL засчитан в покрытие ZEC
  zecReserve: { amountZat: string; attested: true; sig: string };   // amountZat округлён вниз до 0.01 ZEC; подпись над
                                                                    // SHA256("unzeen/verify/v1/reserve"‖chainId‖u32(id)‖u32(zcashHeight)‖u64(amountZat))
}

interface VerifyProof {
  snapshotId: number;
  proofs: {
    asset: AssetId;
    pieces: {
      piece: number; leafIndex: number;
      value: string;                       // базовые единицы, кратно грануле
      blind: string;                       // hex 32 байта
      path: { hash: string; sum: string }[]; // соседи снизу вверх; сторона = бит leafIndex
    }[];
  }[];
  truncated: boolean;
  pad: string;
}
```
Ошибки: существующие (`unauthorized`, `not_found`, `rate_limited`). Лимит на `/api/verify/proof` — 10/мин на ключ. Пустой результат — не ошибка.

RELAYER.md v3 (черновик): `op='anchor'` (`meta: {"memo": "..."}`, без mint/venue, `exec_mode='delayed'`, в `trades` не пишется); таблица `verify_assets` и подписи vault пишет релейер по флагу `pool_meta.verify_request = <snapshotId>`; уважать `verify_freeze_until` при claim.

## 9. Находки и риски (по убыванию)

**HIGH**
- **V1 · Merkle-sum без разбиения раскрывает чужие балансы.** Соседний лист в доказательстве — это **точный** баланс другого пользователя, а у токенов он часто равен сумме одной публичной покупки. *Исправление:* разбиение §2.3. Если его режут ради срока, то хотя бы перемешивание и паддинг, а в README честно: «a proof reveals sibling subtree sums».
- **V2 · Публикация нот или нуллифайеров ради «доказательства резерва ZEC» раскрывает tx депозитов.** *Исправление:* только attestation (§4.2). Запретить в коде и ревью любые выгрузки `cmx`/`nf`/txid пула.
- **V3 · Одинаковый лист в разных снимках** (без `snapshotId`/нового `blind`) позволяет следить за балансом одного пользователя во времени, а значит связывать его изменения с публичными сделками. *Исправление:* §2.4.

**MEDIUM**
- **V4 · Ложная несостоятельность** из-за заданий, исполненных, но не прошедших settle. Это сорвёт демо на глазах судей. *Исправление:* freeze §5.2.
- **V5 · Подставные vault.** Без подписи vault оператор может «одолжить» чужие адреса. *Исправление:* подпись каждого адреса на снимке (§4.1), дёшево.
- **V6 · Эквивокация корней.** Без якоря оператор может отдавать разным пользователям разные корни. *Исправление:* memo-tx в Solana (§2.5). Без якоря в README: «roots are signed but not anchored».
- **V7 · Размер ответа доказательства раскрывает число активов.** *Исправление:* выравнивание до 16 КиБ (§3).

**LOW**
- **V8 · Суточная дельта ZEC-обязательств ≈ поток единственного активного пользователя** (§5.3). Не связывает с ключом или Zcash-tx. Можно сделать публикацию еженедельной.
- **V9 · Хранение доказательств в браузере.** Только скачивание, без localStorage.
- **V10 · Обязательства пользователей, которые не проверяют своё доказательство, оператор может опустить.** Это общее ограничение всех PoL-схем. Строка в README.

## Открытые вопросы для лида / владельца

1. **ZEC-резерв = «attested by operator»** — подтверждаете? Альтернатив без утечки на 16 дней нет (§4.2).
2. **Частота корня:** раз в сутки (рекомендация) или раз в неделю (строже по V8)? Для демо — ручной снимок только на devnet.
3. **Якорь в Solana (memo-tx)** — включаем в MVP? Даёт защиту от эквивокации за ~0,25 дня, и судьи это видят.
4. **Ключ оператора** для подписи корней и резерва: новый ed25519, хранить на зашифрованном томе рядом с сидом пула (N2)? Pubkey — в README и в бандле фронта.
5. **В план:** предлагаю Verify в дни 11–12 вместе с fair-launch. При нехватке времени двигать по порядку урезания до NEAR Intents, а не после. Verify прямо заявлен в FEATURES как ядро «честности», и судьи трека Private Markets его ждут.
