# Анонимный чат под токеном: спецификация и аудит приватности

Автор: analyst · Дата: **2026-10-13** · Основа: FEATURES.md п. 4, API.md v0.10 (заглушки: `op:"chat"` стр. 281, `ChatMessage` стр. 297–300, «Дополнительные эндпоинты» стр. 736–737), review-day2 L5, review-day4 (D1/D2), now-mode (N-2, N-9, N-10), код `core/api/src/{actions.rs,lib.rs,limit.rs,market.rs}`, `web/lib/pad.ts`. Код не правил.
Правило: любая утечка = дисквалификация.

## TL;DR

1. Чат реализуем без новых классов утечек, если соблюдать три вещи. **(а)** Ник считается как HMAC с секретом, который хранится вне БД. Голый `sha256(pk‖mint)` из API.md:298 связывает все ники человека, как только где-то всплывёт его anon pubkey, а такое возможно: дамп БД, QR в видео. **(б)** Чат идёт тем же `POST /api/actions`, тело ровно 1024 байта. Публикация происходит на тех же границах эпох Delayed, что и сделки. В сети отправка сообщения неотличима от buy/sell. **(в)** Сообщения хранятся без anon-ключа: в БД только ник, текст и время пачки.
2. Бейдж creator — это **отдельный ник** создателя в этом чате (вторая метка домена в HMAC). Иначе одно сообщение с бейджем задним числом раскрывает все прошлые сообщения того же ника. Право на бейдж проверяет сервер по `creator_tokens`, публично ключ не раскрывается. Бейдж подтверждает оператор, это честно пишем в UI.
3. Модерация обходится без деанонимизации. Автор может удалить своё сообщение. Создатель может скрыть сообщение в чате своего токена, это видно как «hidden by creator». Сообщение скрывается автоматически после 3 репортов от разных допущенных ключей. Оператор может мьютить пару (ник, mint). Глобального бана по ключу нет. Только текст, ссылки не кликабельны, превью нет. Сроки: backend ~1,5–2 дня, frontend ~1,5 дня, работают параллельно; ревью 0,5 дня. Итого ~2,5 календарных дня.

## 1. Модель сообщения

### 1.1 Что хранится и что отдаётся

Хранятся `id`, `mint`, `nick`, `isCreator`, `text`, время пачки и статус. **Чего нет нигде, ни в БД, ни в ответах:** anon pubkey, подпись запроса, время приёма запроса, IP, `nonce`.

```ts
interface ChatMessage {
  id: string;          // 32 hex, 128 бит случайных
  mint: string;
  nick: string;        // 8 символов Crockford base32 в нижнем регистре, см. §2. UI показывает "anon-" + nick
  isCreator: boolean;  // true только у ника создателя (§3)
  text: string;        // NFC, проверен по §7; сервер его НЕ переписывает
  ts: number;          // unix мс = время границы эпохи, на которой сообщение опубликовано (не время запроса)
}
```

### 1.2 Подпись

Сообщение — это обычный подписанный `POST /api/actions` (схема «Подпись запросов», API.md:767): `op:"chat"` в теле, подпись anon-ключом в заголовках. Отдельной подписи у самого сообщения нет: подпись нужна только серверу, чтобы проверить допуск и лимиты. Публиковать её нельзя, потому что она проверяется pubkey'ем и связала бы все ники ключа (review-day2 L5).

### 1.3 Редактирование и удаление

- **Редактирования нет.** Каждое редактирование добавляет ещё один момент «IP отправил → изменение появилось», а подмену текста после реакций легко использовать для обмана.
- **Удаление автором:** `{op:"chat_delete", id}`. Сервер берёт сообщение, пересчитывает ник для `pk` из заголовка и `mint` сообщения (обычный или ник создателя, по `isCreator`) и сравнивает. Не совпало или сообщения нет → `404 not_found`. Хранить pk для этого не нужно. Удаление применяется **на следующей границе эпохи**, не сразу. Текст стирается из БД в момент применения, `id` остаётся надгробием на 24 ч, чтобы клиенты убрали сообщение у себя (§5.3).

## 2. Ник

```
nick_member  = b32(HMAC-SHA256(K_chat, "unzeen/chat/nick/v1" ‖ chainId[2] ‖ mint[32] ‖ anonPubkey[32] ‖ 0x00))[0..8]
nick_creator = b32(HMAC-SHA256(K_chat, "unzeen/chat/nick/v1" ‖ chainId[2] ‖ mint[32] ‖ anonPubkey[32] ‖ 0x01))[0..8]
b32 = Crockford base32, нижний регистр (алфавит 0123456789abcdefghjkmnpqrstvwxyz), 8 символов = 40 бит
mint[32] = 32 байта base58-декода mint; chainId[2] = байты PoolInfo.chainId
```

**Почему ники не связываются между токенами.**
- `mint` входит в вход HMAC, поэтому ники одного ключа в разных чатах — независимые псевдослучайные строки.
- **Почему с секретом, а не `sha256` (находка C-1 ниже).** Anon pubkey не тайна для всех. Он лежит в `balances`/`deposits` (дамп БД, бэкап, ошибка доступа), в memo депозита (QR на экране и в видео, review-day2 L7) и в заголовках каждого запроса. При голом хэше любой, у кого есть pk, считает ники человека во **всех** чатах и связывает их с его депозитами. С HMAC для этого нужен ещё `K_chat`, а его в БД нет.
- `chainId` нужен для разделения доменов (devnet и mainnet ключи и так разные, но лучше явно).
- 40 бит: случайная коллизия в одном чате при 10⁴ ников ≈ 5·10⁻⁵. Подбор ключа под чужой ник офлайн невозможен (нужен `K_chat`), онлайн каждая попытка — это допущенный ключ с депозитом.
- Ник генерирует сервер, он только ASCII, поэтому юникод-спуфинг ника исключён (§7).

**`K_chat`:** 32 случайных байта, свой для каждой сети. Лежит рядом с age-ключом сида (systemd `LoadCredential`, ARCHITECTURE.md «Хостинг»), **не в Postgres и не в `.env` в репо**. Ротация меняет все ники (все становятся «новыми людьми»). Делать её только при утечке ключа.

**Что остаётся (честно, в README).** Оператор, у которого есть `K_chat` и список pk, может пересчитать ники и связать их с аккаунтами. Он и так видит pk в каждом запросе: это та же модель доверия к оператору, что у реестра. Дамп одной БД ники не раскрывает. Связывание по стилю текста, времени суток или одинаковому тексту в разных чатах — поведение пользователя (§6.4).

## 3. Бейдж creator

- Создатель (ключ из `creator_tokens` для этого mint) по желанию пишет с `showCreatorBadge: true`. Тогда сервер проверяет права и публикует сообщение под **`nick_creator`** с `isCreator: true`. Нет прав → `403 not_creator`.
- **Почему отдельный ник (находка H-1).** Если бейдж — флаг на сообщении при том же нике, одно сообщение с бейджем показывает всем, что **все** прошлые и будущие сообщения этого ника тоже от создателя. С отдельным ником обычные сообщения создателя в этом чате остаются неотличимы от остальных.
- **Доказательство, не раскрывая ключ.** Публичного криптодоказательства нет и в MVP не будет. Подпись anon-ключом раскрыла бы pk, а ZK — это roadmap («Доказать, что ты создатель»). Бейдж — **утверждение оператора**: сервер проверил реестр. UI: «Verified by the Unzeen pool: this nickname belongs to the account that launched the token.» На цепочке связи нет: creator-адрес запуска — свежий ключ пула.
- Бейдж есть только у Unzeen-запусков (`create`/`fl_create`). У чужих токенов бейджа нет.
- T1 не нарушается: бейдж не публикует ни долю, ни продажи создателя. Предупреждение в UI перед первым постом с бейджем: «Posting as creator uses a separate nickname. Everything you post with the badge is publicly the creator's. Your regular nickname here stays unlinked.»

## 4. Антиспам

### 4.1 Допуск (минимальный баланс)

- **Правило (R5):** ключ допущен, если на момент запроса `available + held` ZEC + `Σ holdings[mint].amount × последняя цена тика (intel_prices) / lamportsPerZecSell` ≥ `PoolInfo.chat.minAccountZat`. Токены без цены считаются 0. Значения по умолчанию: mainnet 0,05 ZEC, devnet 0,001 TAZ (env `UNZEEN_CHAT_MIN_ACCOUNT_ZAT`). Ключи для судей заранее пополнены, их это не затрагивает.
- **Почему не «ZEC на балансе».** Трейдер, у которого всё в токенах, не смог бы писать в чате своего же токена. А «сумма депозитов за всё время» слабее: можно гонять одни и те же ZEC через выводы и кормить ими новые ключи. Текущая стоимость ограничивает число одновременно допущенных ключей бюджетом спамера.
- **Как проверить, не раскрывая баланс.** Порог публичен. Ответ знает только автор подписанного запроса: `403 chat_not_eligible`, в `message`/`details` **нет сумм**. Ответ паддится до 1024, как у всех действий, поэтому сетевой наблюдатель не отличит отказ от успеха по размеру, а отличие по статус-коду ему ничего не даёт: тело в TLS. Допуск — свойство ключа в момент запроса, в БД он не записывается.
- `frozen` → `423 balance_frozen`, как у любого действия (API.md:438).
- Наблюдатель видит только то, что у каждого ника в чате аккаунт выше порога. Это одинаково для всех.

### 4.2 Лимиты частоты

| Лимит | Значение | Где |
|---|---|---|
| На ключ | 1 сообщение / 10 с, 20 / ч, 100 / сутки (вместе с `chat_delete`, `chat_report`, `chat_hide`) | in-memory `Limiter` (`core/api/src/limit.rs`, ключ хэшируется случайным ключом процесса, на диск не пишется) |
| На mint | ≤ 50 сообщений в одной пачке; больше → `429 rate_limited` для новых | счётчик pending в БД |
| На пул | ≤ 2000 pending всего | счётчик |

Лимиты по нику в БД **не храним**: для этого нужна строка «ник ↔ счётчик ↔ время» на каждый запрос. После рестарта процесса лимиты обнуляются, и это приемлемо.

### 4.3 Что видит оператор

| Где | Что | Сколько живёт |
|---|---|---|
| Запрос в памяти | pk, IP (не логируется), mint, текст, флаги | время обработки |
| `api_nonces` | `(pk, nonce)` + ответ для идемпотентного повтора (там есть `id` сообщения) | до `ts + 120 с`, затем удаляется вместе с nonce |
| `chat_messages` | id, mint, nick, isCreator, text, publish_after, ts пачки, статус | §6 |
| `chat_reports` | id сообщения, `reporter_tag = HMAC(K_chat, "unzeen/chat/report/v1" ‖ id ‖ pk)` | 7 дней или до удаления сообщения |
| `Limiter` | хэш pk со случайным ключом процесса | до рестарта |
| Логи | маршрут-шаблон, статус, мс (как сейчас в `lib.rs:212`) | — |

**Запрещено:** писать chat в `actions`/`ledger_ops`, показывать его в `Portfolio.actions`, логировать текст/mint/ник/pk, хранить pk в любой chat-таблице, записывать время приёма запроса.

## 5. Доставка и тайминг

### 5.1 Отправка

- `POST /api/actions` c `op:"chat"` (уже есть в `SignedAction`, API.md:281). **Тело ровно 1024 байта** (`PAD_MIN` в `web/lib/pad.ts:8`). Сервер отвечает `400 bad_request` на любую chat-операцию, у которой длина тела ≠ 1024. Так гарантируется, что тело chat в сети такого же размера, как buy/sell/withdraw, и не выдаёт длину текста (находка H-2). Ответ паддится до 1024 (`padded`, `lib.rs:220`).
- Отсюда предел текста: JSON-строка текста (`JSON.stringify(text)` в UTF-8, с кавычками и экранированием) ≤ **800 байт** и ≤ 280 скалярных значений Unicode. Остальное тело (op, mint до 44 символов, флаги, `"pad":""`) укладывается в ~170 байт. Фронт проверяет до подписи, сервер проверяет те же правила.
- Квитанция: `{ id, status: "queued", nick }`. По `nick` клиент узнаёт свой ник в этом чате, отдельный запрос «мой ник» не нужен (он связал бы ключ с просматриваемым mint).

### 5.2 Публикация пачками (R3)

- При приёме сервер ставит `publish_after = now` (или `now + rand(120..300) с` при `slow: true`) и `status = pending`.
- Публикатор в core: цикл `sleep(epochs.delay(false))`, где граница берётся из **того же** `Epochs`, что у Delayed-сделок (`actions.rs:168-213`). На каждой границе B одной транзакцией: все `pending` с `publish_after ≤ B` → `published`, `ts = B`, `seq` выдаётся из последовательности **в случайном порядке** (`ORDER BY random()`). Затем применяются удаления и скрытия, накопленные к B.
- **Нельзя** звать `epochs.delay_at(_, будущее_время)` для «slow»: метод сдвигает общий указатель границы и сломает расписание сделок. «Slow» делается только через `publish_after`.
- **Почему та же граница.** Сетевой наблюдатель видит POST в T и результат на ближайшей границе: сделку в цепочке и/или сообщение в чате. Пока граница общая, он не знает, что именно отправил этот IP. Чат становится прикрытием для сделок, и наоборот. При отдельном расписании чата совпадение границ сразу показало бы тип запроса.
- Публичный `ts` = время границы. Время приёма не хранится и не отдаётся.

### 5.3 Получение (R4)

- **WS для чата нет.** `/ws/chat/:mint` из API.md удалить. Поводов три: мгновенный пуш на каждое сообщение, отдельный канал и размеры кадров по mint. Чат и так публикуется раз в 30–60 с, так что опрос ничего не теряет.
- `GET /api/tokens/:mint/chat?after=<cursor>` — фронт опрашивает **с фиксированным интервалом 10–15 с (джиттер), пока открыта страница токена, на любой вкладке**. Опрос не ускоряется, не останавливается и не начинается из-за собственного сообщения (урок N-2).
- Первая загрузка — `GET /api/tokens/:mint/chat?limit=50` (последние). Листание назад — `?before=<cursor>`.
- Своё сообщение клиент сразу показывает локально как «Posting with the next batch…» и убирает пометку, когда `id` из квитанции пришёл в опросе. Отдельного опроса статуса нет.
- Ответы публичные, одинаковые для всех: без подписи и cookies, `Cache-Control: public, max-age=5`, паддинг до кратного 4096. Размер ответа может намекнуть, какой чат открыт. Это low: тот же mint и так виден по размерам `/api/tokens/:mint`, свечей и `/ws/feed?mint=`, а автора чат не раскрывает.

### 5.4 Связь чата с торговлей

| Сценарий | Риск | Мера |
|---|---|---|
| Сделка X на границе B, ник N в чате X на той же границе или на следующей; повторяется несколько раз | Ник N статистически связывается с сделками пула по X, видны его размеры и PnL | R6: если клиент по локальной истории видит своё действие по этому mint за последние 10 мин, `slow` в композере включён по умолчанию с подписью «Delayed 2–5 min so your message doesn't line up with your trade». Пользователь может выключить. Публичного маркера slow нет |
| Текст «aped 1 ZEC», адрес вывода, сумма | Самораскрытие | Клиент мягко предупреждает: текст содержит сумму своего действия за 24 ч (±1 %) или свой адрес вывода / UA / base58-адрес (§7.3) |
| Пополнил → сразу первое сообщение новым ником | Связь Orchard-tx в блоке ↔ появление ника (как N-10) | То же мягкое предупреждение, что для сделок; сервер уже зачисляет на `K + r` |
| Множество сообщений одного ника против POST-времён одного IP | Атака пересечением: IP, который POST'ил перед каждым сообщением N | Против сетевого наблюдателя защищает только объём. R8 (noop-трафик) это ломает. В README: «use Tor/VPN» |
| Now-сделка + чат | — | У чата нет режима Now |

## 6. Модерация, хранение, контент

### 6.1 Модерация без деанонимизации

| Действие | Кто | Как проверяется | Публично |
|---|---|---|---|
| `chat_delete {id}` | автор | пересчёт ника (§1.3) | сообщение исчезает на границе (`removed: deleted`) |
| `chat_hide {id}` | создатель токена | `creator_tokens` по pk и mint сообщения; иначе `403 not_creator` | плашка «Hidden by creator» (`removed: creator`); злоупотребление видно |
| `chat_report {id, reason: "spam"\|"scam"\|"abuse"}` | любой допущенный ключ | дедуп по `reporter_tag` (§4.3); свой же репорт повторно → 200, без эффекта | при ≥ 3 разных репортерах — «Hidden after reports» (`removed: reports`) на ближайшей границе |
| CLI `unzeen-api chat hide <id>` / `chat mute --mint --nick --hours` / `chat purge --mint` | оператор | — | `removed: operator`; muted ник получает `403 chat_muted` |

- Глобального бана нет: он требует найти ключ по нику, то есть деанонимизировать. Мьют работает по (ник, mint). Чтобы обойти его, спамеру нужен новый ключ с аккаунтом выше порога.
- Репорт ничего не показывает до порога. Число репортов не публикуется.
- `reporter_tag` содержит `id` сообщения, поэтому репорты одного ключа на разные сообщения не связываются.

### 6.2 Хранение (ретеншн)

| Данные | Срок |
|---|---|
| Опубликованные сообщения | 30 дней и не больше 1000 последних на mint (janitor раз в час) |
| Удалённые / скрытые | текст стирается в момент применения; надгробие `{id, reason}` — 24 ч |
| `chat_reports` | 7 дней или до удаления сообщения |
| `chat_mutes` | до `until` |
| pending | до публикации (≤ 5 мин) |
| Бэкапы | нет (решение по VPS, ARCHITECTURE.md) |

Публичные сообщения могут сохранить третьи стороны, это нормально. Ретеншн защищает содержимое БД.

### 6.3 Ссылки и картинки

- **Только текст.** Без картинок, markdown, эмбедов, превью ссылок и автолинковки: URL показываются обычным текстом. Превью означало бы запрос сервера или браузера к чужому хосту, а это утечка IP и интереса. Кликабельные ссылки — фишинг.
- Адреса Solana (CA) — обычный текст. Ради них чат и существует.

### 6.4 Что пишем в README

Чат-ники отдельные для каждого токена и не связываются между токенами ни публично, ни по дампу БД. Сообщения публикуются пачками вместе со сделками. Оператор технически может связать ник с аккаунтом. Стиль письма, одинаковые тексты и время активности могут вас связать. Для защиты от сетевого наблюдателя — Tor/VPN.

## 7. Безопасность контента

### 7.1 Канонический текст (сервер отвергает, а не переписывает)

Подпись покрывает текст, поэтому сервер **не меняет** его. Клиент нормализует до подписи, сервер проверяет и на любое нарушение отвечает `400 chat_text_invalid`. Правила одинаковы в Rust и TS, юникод-таблиц категорий нет: только явные диапазоны, чтобы версии Unicode не разошлись.

1. `text === text.normalize("NFC")` (Rust: `unicode_normalization::is_nfc`).
2. 1–280 скалярных значений (`[...text].length` / `text.chars().count()`); `JSON.stringify(text)` ≤ 800 байт UTF-8.
3. Нет пробела в начале и конце; ≤ 3 символов `\n` всего, нет `\n\n\n`. Других переводов строк нет.
4. Запрещённые кодовые точки:
   - U+0000–U+0009, U+000B–U+001F, U+007F–U+009F (C0/C1, в том числе `\t`, `\r`, U+0085);
   - bidi: U+061C, U+200E, U+200F, U+202A–U+202E, U+2066–U+2069;
   - невидимые: U+00AD, U+034F, U+115F, U+1160, U+17B4, U+17B5, U+180E, U+200B, U+200C, U+2060–U+2064, U+3164, U+FEFF, U+FFA0;
   - U+2028, U+2029, U+FFF9–U+FFFC;
   - private use: U+E000–U+F8FF, U+F0000–U+FFFFD, U+100000–U+10FFFD;
   - теги и супплементарные селекторы: U+E0000–U+E007F, U+E0100–U+E01EF;
   - нехарактеры: U+FDD0–U+FDEF, любые U+xFFFE/U+xFFFF;
   - одиночные суррогаты (на фронте `/\p{Cs}/u`; serde_json их и так не пропустит).
   - Разрешены U+200D (ZWJ, эмодзи) и U+FE00–U+FE0F.
5. Зальго: не больше 2 подряд кодовых точек из U+0300–U+036F, U+1AB0–U+1AFF, U+1DC0–U+1DFF, U+20D0–U+20FF, U+FE20–U+FE2F.
6. **Сид-фраза:** ≥ 12 слов из английского списка BIP-39 (регистронезависимо, разделители — пробелы и знаки препинания) → отказ на клиенте (блок) и на сервере (`chat_text_invalid`, `details: "looks like a recovery phrase"`). Это защищает пользователя от самого себя.

Векторы: `core/testdata/chat-vectors.json`. В нём: `text` → valid / reason (по случаю на каждый пункт), `nick` (фиксированный тестовый `K_chat`, pk, mint, chainId → member/creator), пример тела chat ровно 1024 байта с подписью.

### 7.2 XSS и инъекции

- Фронт: текст только текстовым узлом React. Никаких `dangerouslySetInnerHTML`, markdown-рендера и linkify. Текст оборачивается в `<bdi>` (`unicode-bidi: isolate`), чтобы RTL не переставлял ник и бейдж. `overflow-wrap: anywhere`, `white-space: pre-line`.
- Текст чата не попадает в `<title>`, OG-мета и SSR-HTML: чат грузится только клиентом.
- Бек: только параметризованные запросы (sqlx). Ответ `application/json` + `nosniff` (уже есть). В `ApiError.message` текст сообщения не попадает никогда.
- Ник и бейдж — отдельные элементы со своим стилем. Текст вида «anon-7k3q9m2x ✓creator:» визуально остаётся внутри пузыря чужого сообщения. Ник — только ASCII base32 от сервера, спуфинга ника гомоглифами нет.

### 7.3 Мягкие предупреждения клиента (не блок)

Предупреждаем, если текст содержит: base58-строку 32–44 символа, которая не mint этой страницы; UA/`u1…`/`utest1…`/t-адрес; сумму своего действия за 24 ч (±1 %); свой адрес вывода из локальной истории. Текст: «This looks like an address or amount linked to you. Posting it publicly can connect you to it.»

## 8. Находки по существующим заглушкам (по убыванию серьёзности)

**C-1 (critical, если реализовать как написано) · `docs/API.md:298`, `web/lib/api/types.ts:298` · Ник = `sha256("unzeen/chat/v1" ‖ pk ‖ mint)[:8]`.**
Любой, у кого есть pk, связывает все ники человека по токенам и с его депозитами. pk есть в дампе БД (`balances`, `deposits.anon_pubkey`), в memo на QR (видео, скриншоты) и у оператора. 32 бита без секрета ещё и подбираются офлайн: ~2³² генераций ed25519, это часы на CPU. После подбора хватает одного депозита, чтобы писать под чужим ником.
→ §2: HMAC с `K_chat` вне БД, 40 бит.

**H-1 · `API.md:281` (`showCreatorBadge` на сообщении) · Бейдж на том же нике раскрывает все прошлые сообщения этого ника как сообщения создателя.**
→ §3: отдельный `nick_creator`.

**H-2 · `web/lib/pad.ts:7-8` + API.md:60 · Тело длиннее 1024 уходит в бакет 1280/1536/…**
По размеру видно, что это не сделка, и виден бакет длины, который совпадает с длиной опубликованного сообщения. Получается прямая связь «IP → это сообщение».
→ §5.1: chat-тело ровно 1024, сервер отвергает другую длину; текст ≤ 800 байт в JSON.

**H-3 · Будущая реализация через общий путь `build()` (`core/api/src/actions.rs:654-660`) · Строка в `actions` с pk + kind + mint + временем, плюс показ в `Portfolio.actions`.**
Это вечная связь ключ ↔ чат ↔ время (как D1).
→ Обработчик chat-операций — отдельная ветка до `build`, как `claim`. Ни `actions`, ни `ledger_ops`, ни hold.

**M-1 · `API.md:737` `/ws/chat/:mint` · Мгновенный пуш = «POST в T → сообщение в T+0,1 с».**
→ §5.2–5.3: пачки + опрос; WS убрать.

**M-2 · Допуск «минимальный баланс ZEC» (FEATURES п. 4) по буквальному смыслу** не пускает в чат держателей токена с нулевым ZEC и подталкивает держать ZEC на балансе.
→ R5.

**L-1 · `docs/submission/README.draft.md:298`** («chat is not implemented»): обновить после реализации; строка 426 станет верной только после C-1.

**L-2 · Размер публичных ответов чата** косвенно выдаёт, какой чат открыт. Не хуже того, что уже выдают `/api/tokens/:mint` и свечи. Паддинг до 4096 — да; фиксированный размер — нет (трафик).

### Публичное чтение

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/api/tokens/:mint/chat?limit=50` | `ChatPage`: последние опубликованные, новые первыми |
| GET | `/api/tokens/:mint/chat?before=<cursor>&limit=50` | `ChatPage`: старше курсора |
| GET | `/api/tokens/:mint/chat?after=<cursor>` | `ChatPage`: всё опубликованное и удалённое после курсора, по возрастанию `seq`, ≤ 100 (`more: true`, если есть ещё) |

Без подписи и cookies, ответ одинаков для всех, `Cache-Control: public, max-age=5`, паддинг до кратного 4096. Mint не base58-32 → 400. Mint не в публичном списке → `200 { messages: [], removed: [], cursor: "0", more: false }`, без 404 и без постановки в очередь индексатора. Без `features.chat` → 404 (как неизвестный путь).

```ts
interface ChatMessage {
  id: string; mint: string;
  nick: string;          // 8 символов Crockford base32 (lower). HMAC(K_chat, …), см. «Чат». pk/подпись НИКОГДА не отдаются
  isCreator: boolean;    // ник создателя (отдельный от его обычного ника в этом чате)
  text: string;
  ts: number;            // unix мс — граница эпохи публикации
  seq: string;           // порядковый номер публикации (десятичная строка); порядок внутри пачки случайный
}
interface ChatPage {
  messages: ChatMessage[];
  removed: { id: string; reason: "deleted" | "creator" | "reports" | "operator" }[];  // надгробия ≤ 24 ч
  cursor: string;        // максимальный seq событий в ответе (передать в after=)
  more: boolean;
  pad: string;
}
```

Новые коды ошибок: `chat_text_invalid` (400), `chat_not_eligible` (403), `chat_muted` (403), `not_creator` (403).

### Миграция `0016_chat.sql` (номер после `0015_rebalance.sql`)

```sql
CREATE SEQUENCE chat_seq;
CREATE TABLE chat_messages (
  id            BYTEA PRIMARY KEY CHECK (length(id) = 16),
  mint          TEXT NOT NULL,
  nick          TEXT NOT NULL CHECK (nick ~ '^[0-9a-hjkmnp-tv-z]{8}$'),
  is_creator    BOOLEAN NOT NULL,
  text          TEXT,                       -- NULL после удаления/скрытия
  status        TEXT NOT NULL CHECK (status IN ('pending','published','removed')),
  publish_after TIMESTAMPTZ NOT NULL,       -- не время приёма для slow; для обычных — грубо (до секунды), стирается при публикации
  ts            TIMESTAMPTZ,                -- граница публикации
  seq           BIGINT UNIQUE,              -- выдаётся при публикации и заново при удалении (событие removed)
  removed_reason TEXT CHECK (removed_reason IN ('deleted','creator','reports','operator')),
  remove_at     TIMESTAMPTZ,                -- запрошенное удаление: применяется на границе
  removed_at    TIMESTAMPTZ
);
CREATE INDEX ON chat_messages (mint, seq);
CREATE TABLE chat_reports (msg_id BYTEA NOT NULL, reporter_tag BYTEA NOT NULL, created_day DATE NOT NULL,
                           PRIMARY KEY (msg_id, reporter_tag));
CREATE TABLE chat_mutes (mint TEXT NOT NULL, nick TEXT NOT NULL, until TIMESTAMPTZ NOT NULL, PRIMARY KEY (mint, nick));
-- Права: только роль API. Роль релейера доступа не имеет.
```

При публикации `publish_after := ts`, чтобы в БД не осталось времени приёма (у обычных сообщений оно ≤ границы и могло бы быть точным).

## 11. Открытые вопросы для лида

1. R1–R6: подтверждаем? R1 и R2 меняют формулировку FEATURES п. 4 («H(anonPubkey ‖ mint)» → HMAC с секретом; бейдж = отдельный ник).
2. Порог допуска: 0,05 ZEC на mainnet устраивает? От курса ZEC зависит, насколько дорог сибил.
3. Создатель скрывает сообщения в своём чате (`chat_hide`): включаем? Это удобно и похоже на pump.fun, но создатель может цензурировать FUD. Плашка «Hidden by creator» делает это видимым.
4. R8 (noop-трафик) — берём? Это единственная мера против атаки пересечением для чата и для сделок, и судьи это оценят.
5. Задержка 30–60 с в чате для UX приемлема? Альтернатив без утечки нет: мгновенная публикация = прямая связь IP ↔ сообщение.
