# Ревью дня 2: сканер, протокол API v0.1, сквозная приватность

Автор: analyst · Дата: **2026-10-12** · Объект: коммит `10474fc` (`core/scanner`, `infra/`, `.env.example`), `docs/API.md` v0.1, `docs/ARCHITECTURE.md`, `docs/FEATURES.md`, `docs/FRONTEND.md`, бегло `web/lib` (только чтение).
Правило: любая утечка связи пользователь ↔ сделка = дисквалификация, поэтому «утечка, известная только оператору» отделена от «утечки третьим лицам / публике».

## TL;DR

1. **Сканер написан аккуратно** (без git-зависимостей, точные пины, секреты в git не попали, mainnet-send закрыт флагом и потолком). Но это CLI, не сервис. На нём **нельзя строить реестр как есть**: курсор теряет депозиты (баг), unmined/реорганизованные ноты выглядят как обычные, при сетевой ошибке `--watch` падает, а stdout печатает связку txid ↔ сумма ↔ memo (anon_pubkey, refund).
2. **Протокол `unz1` в целом верный** (domain separation, chain_id, nonce, expiry, подпись покрывает refund). Есть четыре дыры. Не определено, **кто подписывает memo**: бек не может, ключ только в браузере. Нет правила «депозит пропал после reorg уже после зачисления». Нет минимальных сумм (дешёвый DoS сжигает SOL на ренте ATA). Не определён повтор `nonce` при оплате того же QR дважды.
3. **Три приватностные мины в планах, кода по ним ещё нет, но все ведут к дисквалификации:**
   (а) `/verify` через публикацию viewing key пула раскрывает всех. В memo лежат anon_pubkey и refund, а OVK раскрывает всех получателей выплат.
   (б) Режим «оплата за действие» при депозите из transparent/Sapling/Orchard публично светит сумму и время, а сделка следует через 1–2 минуты.
   (в) Вывод токенов на «новый» адрес без газа: юзер вынужден пополнить его SOL со своего кошелька. По умолчанию «умный вывод» выключен, это нужно перевернуть.
   Плюс high-утечки третьим лицам: lightwalletd (zec.rocks) видит, какие txid интересны пулу; access-логи хостинга с anon_pubkey в URL; публичная статистика в реальном времени.

### CRITICAL

**C1 · `docs/FRONTEND.md:36` (`/verify` — «viewing key»), `docs/ARCHITECTURE.md:75` (roadmap «публикация viewing key»), `docs/analysis/hackathon-rules.md` §3 п.5 (мой же совет), `core/scanner/src/send.rs:120` (`OvkPolicy::Sender`) · Публикация UFVK пула деанонимизирует всех.**
UFVK = IVK + OVK. IVK расшифровывает каждый входящий memo, а в `unz1` открытым текстом лежат `anon_pubkey`, `mint`, `min_out`, refund UA и Solana-адрес вывода. OVK (при `OvkPolicy::Sender`) расшифровывает каждую выплату: получатель, сумма, время. С UFVK любой соберёт полный реестр «депозит → anon-ключ → команда → куда выплачено».
*Исправление:* UFVK/IVK **никогда** не публиковать, свою прошлую рекомендацию отзываю. Verify строить так:
- (1) Solana-резервы vault: публичные адреса и балансы;
- (2) обязательства: Merkle-sum-tree балансов по листьям `H(anon_pubkey ‖ salt_epoch)`; корень публикуется, юзер в `/portfolio` получает inclusion-proof;
- (3) лента ↔ Solana-tx: каждая запись ленты кликается в эксплорер;
- (4) shielded-резерв ZEC: честно «attested by operator» (подписанное заявление), без ключа.

Для выплат `OvkPolicy::Discard`, чтобы утечка сида/OVK в будущем не раскрывала историю выплат. Сначала проверить, что ничего не ломается: OVK нужен только для собственной истории отправок, реестр её и так ведёт.

**C2 · `docs/ARCHITECTURE.md:44-56` (режим «оплата за действие»), `FEATURES.md:7` · Сумма и время депозита публичны, сделка следует за ними.**
Если юзер платит из transparent-адреса (типично после вывода с биржи), из Sapling или из старых Orchard-нот, межпуловый переход в Ironwood публикует `valueBalance`, то есть точную сумму и блок. Это следует из устройства turnstile. Для Orchard→Ironwood нужно сверить с ZIP 258: **не подтверждено построчно, но value balance бандла публичен по построению**. Через 1–2 минуты пул покупает на Solana на ту же сумму × курс. Дальше простая сверка: KYC-биржа → t-адрес → «unzeen купил X $PEPE». Даже при Ironwood→Ironwood депозите время блока + единственная сделка unzeen в окне = связь для любого, кто знает время отправки юзера (его кошелёк/lightwalletd, см. H1).
*Исправление (по убыванию предпочтения):*
- (а) **вырезать режим «оплата за действие» из демо** и оставить только режим баланса: экономит дни и снимает класс утечек;
- (б) если оставлять: фиксированные номиналы (0.01/0.05/0.1/0.5 ZEC), исполнение эпохами (раз в N блоков, случайная задержка 2–10 блоков), сумма сделки ≠ сумма депозита (округление вниз до бакета, остаток на баланс anon-ключа).

В обоих случаях UI депозита должен прямо говорить: «Send from a shielded (Ironwood) balance. Funds sent from a transparent address or an older pool reveal the amount» — и тут же давать инструкцию «сначала shield/migrate в своём кошельке и подождите».

**C3 · `FEATURES.md:11,18`, `API.md:197-198` (`withdraw_token`, `smart` по умолчанию выключен) · Вывод токенов связывает основной кошелёк юзера со сделкой.**
Чтобы перевести или продать токены с «нового» адреса, юзеру нужен SOL на газ. Почти все пополнят адрес со своего основного кошелька: основной кошелёк ↔ новый адрес ↔ vault-transfer ровно на X токенов ↔ «unzeen купил X». Вторая утечка: точное совпадение суммы вывода и суммы покупки, особенно сразу после покупки.
*Исправление:*
- `gasDrop` **включён по умолчанию** (SOL на ~2–3 tx + рента ATA);
- вывод с другого vault, а не с того, что покупал;
- случайная задержка по умолчанию (≥ 1–2 эпохи, а не 0);
- предупреждение в UI, если сумма вывода равна сумме одной из последних покупок;
- `to: string[]` (части) — **отдельными** tx с разных vault, никогда одной tx;
- бек проверяет, что `to` без истории (`getSignaturesForAddress` пусто), иначе warning.

### HIGH

**H1 · `core/scanner/src/sync.rs:259-275` (`fetch_tx` → `GetTransaction`), `config.rs:36-41` (zec.rocks по умолчанию), `infra/README.md:44-47` · Оператор lightwalletd видит, какие tx — депозиты в Unzeen, и может связать их с IP юзера.**
Пул запрашивает `GetTransaction` только для своих tx. Оператор zec.rocks узнаёт множество txid-депозитов и время их обработки. ZODL и другие кошельки часто ходят на тот же zec.rocks: `SendTransaction(tx)` с IP юзера, а через блок `GetTransaction(тот же txid)` с IP пула. Получается IP юзера ↔ депозит в Unzeen, а в C2-режиме ещё и ↔ сделка. Это третья сторона, а не оператор пула.
*Исправление:*
- в демо: **запрашивать все tx с Ironwood/Orchard-actions из каждого сканируемого компактного блока**, а не только свои. На mainnet это десятки tx на блок, приемлемо; на testnet единицы. Тогда оператор видит «пул качает всё»;
- альтернатива: `zcash_client_backend` фича `tor`, а для GetTransaction — разные эндпоинты (zec.rocks / na.zec.rocks / свой);
- в README честно: «self-host lightwalletd or Tor in production».

`init` (`wallet.rs:73`) светит birthday, это low.

**H2 · `API.md:324` («повторный скан после reorg ничего не дублирует»), `sync.rs:207-220`, `deposits.rs:69-77`, `main.rs:153-161` · Нет защиты от депозита, исчезнувшего после зачисления.**
Проверено в `zcash_client_sqlite-0.23.0-pre.1/src/wallet.rs` (`truncate_to_height`): при reorg tx не удаляются, а получают `mined_height = NULL`. Ноты остаются в `v_received_outputs`, и сканер продолжает их выдавать (с `height=unmined`). Если зачислить на 1 подтверждении, а депозит после reorg не вернётся (double-spend), пул уже потратил SOL. Идемпотентность по `(anon_pubkey, nonce)` защищает от дублей, но не от «депозита больше нет».
*Исправление:*
- статусы `seen` (mempool/0 conf), `confirmed` (≥ K), `credited`;
- K = 3 для зачисления на баланс в демо и 10 для mainnet-сумм выше порога; это совпадает с правилом трат untrusted-нот (10 conf);
- реестр каждый цикл перечитывает `mined_height` уже зачисленных нот. Если `NULL` дольше X блоков, это алерт и заморозка баланса anon-ключа (не уводить в минус молча);
- ключ идемпотентности зачисления — `(txid, pool, action_index)`, а не только `(anon_pubkey, nonce)`.

**H3 · `API.md:126,173-185,304` · Не определено, кто подписывает memo. Сервер может подменить refund.**
`IntentRequest.sig` подписывает неизвестно что. При этом «`PaymentRequest.memo` — готовая строка, фронт её не собирает и не разбирает», а `sig = ed25519(anon_sk, …nonce, expiry…)`. Бек не владеет `anon_sk` и не может собрать подписанный memo, а клиент не знает `nonce`/`expiry`, которые выбирает бек. Если сделать «бек присылает байты, фронт подписывает не глядя», скомпрометированный или ошибочный бек подставит свой refund/withdraw_to, и подпись это «узаконит».
*Исправление:* **memo собирает и подписывает фронт** (общий кодек TS/Rust + тест-векторы в API.md). `nonce` и `expiry` выбирает клиент, бек только валидирует. Для `deposit` HTTP вообще не нужен: UA пула статичен, фронт строит ZIP-321 локально, и `/api/deposit` можно убрать (меньше IP ↔ anon_pubkey). `/api/intents` остаётся только для `create` (передача meta) и статуса.

**H8 · `ARCHITECTURE.md:69` («исполняются за секунды») · Тайминг для сетевого наблюдателя.**
ISP, провайдер, CDN или корпоративная сеть видят TLS-запрос юзера к unzeen в T, а «unzeen купил» появляется в T+2 с. При малом числе активных юзеров (в судейский период их единицы) это прямая связь личности со сделкой без всякого доступа к оператору. Размер POST тоже различим.
*Исправление:*
- исполнение эпохами: батч раз в 3–10 с плюс случайный джиттер 0–20 с на действие, по умолчанию, с опцией «Instant (less private)»;
- паддинг тел запросов до фиксированного размера;
- в README — Tor/.onion как roadmap.

На странице приватности честно указать: «timing protection = delay + batching».

**H9 · `API.md:128` (`/api/portfolio/:anonPubkey`) + хостинг · anon_pubkey в URL оседает в access-логах третьих лиц.**
Vercel, Cloudflare и nginx по умолчанию пишут IP + путь + время. Pubkey в пути — это готовая запись «IP ↔ anon-ключ» у хостера.
*Исправление:*
- `GET /api/portfolio` без pubkey в пути (pubkey только в заголовке; заголовки по умолчанию не логируются);
- на сервере отключить access-логи или писать без IP и без query;
- фронт не на сервисах с неотключаемым логированием IP, либо API на своём VPS.

Аналитика (Vercel Analytics и т. п.) запрещена.

**H10 · `API.md` (нет правила) · DoS дешёвыми депозитами и действиями.**
Депозит стоит атакующему около 10 000 zat (ZIP-317: 2 логических действия × 5 000 zat). Каждая нота потом стоит пулу ~5 000 zat на трату, а пыль ниже этой суммы — чистый убыток. В режиме «за действие» каждый крошечный `buy` нового mint заставляет vault платить ренту ATA ≈0.0015–0.002 SOL плюс tx-fee. Получается дешёвый слив SOL, плюс по одному `GetTransaction` на каждую tx.
*Исправление:*
- `MIN_DEPOSIT_ZAT` (например 100 000 = 0.001 ZEC); ниже порога — не зачислять, не исполнять, не фетчить повторно (оставить пулу как пыль);
- `MIN_ACTION_LAMPORTS` ≥ (рента ATA + fee) × k;
- комиссия Unzeen за первую покупку mint на vault покрывает ренту;
- rate-limit на HTTP по pubkey и in-memory токен-бакет по IP без записи IP.

Для команд повтор `(pk, nonce)` ведёт к зачислению суммы на баланс `anon_pubkey` (подпись валидна) без повторного исполнения. Несколько нот в одной tx с одинаковым memo суммируются.

Нужно подписывать **сырой** request-target и сверять его до роутинга; дубли ключей в query запрещены; прокси не переписывает путь.

  - (в) Хранилище nonce — Postgres (а не in-memory), иначе рестарт в пределах окна разрешает replay. Хранить до `ts + 60 с + запас`, а не «120 с с момента приёма».

## Что внести в API.md

1. **Кто строит memo:** «`unz1` собирает и подписывает клиент. Бек его только валидирует». Добавить тест-векторы (hex входа → строка `unz1:` → подпись на фиксированном ключе). `/api/deposit` убрать или сделать необязательным: UA пула отдаётся через `GET /api/pool` (UA + `chain_id` + минимумы), ZIP-321 строится на клиенте.
2. **Подтверждения и статусы депозита:** `seen` (0-conf) → `confirmed` (≥ K, K в `GET /api/pool`) → `credited`. Что происходит при reorg после `credited`: алерт и заморозка, но не минус.
3. **Идемпотентность:** зачисление — по `(txid, pool, action_index)`; исполнение команды — по `(anon_pubkey, nonce)`. Повтор nonce зачисляет сумму на баланс без исполнения. Для `op=deposit` nonce не уникализируется. Несколько нот в одной tx с одинаковым memo суммируются.
4. **`expiry`** сравнивается со временем блока, в котором tx замайнена.
5. **Минимумы:** `MIN_DEPOSIT_ZAT`, минимальная сумма действия. Ниже порога — не зачислять. Отдавать в `GET /api/pool`.
6. **ops в memo:** явно перечислить, какие ops доступны в режиме «за действие» (рекомендую buy/sell/create/deposit). Для `withdraw` — где сумма. Либо добавить `claim`, `withdraw_zec`.
7. **Исправить размеры:** 153 / 185 / 196 байт.
8. **Получатели выплат:** только UA или адреса с Orchard/Ironwood-receiver. Transparent и Sapling-only — `bad_request`.
9. **Подпись HTTP:** в сообщение добавить строку `chain_id` (hex) после домена. `path?query` — сырой request-target, дубли query-ключей запрещены. Nonce хранится в БД до `ts + 60 с + 60 с`. Повтор с тем же nonce возвращает исходный ответ (идемпотентно), `409` — только если тело другое. Strict-верификация ed25519.
10. **Портфель:** `GET /api/portfolio` (pubkey только в заголовке), не в пути.
11. **Id:** intent/action/order — 128 бит случайных. `GET /api/actions/:id` — подписанный. `GET /api/intents/:id` — без `tx`/времени или подписанный.
12. **Исполнение:** в `/api/actions` документировать батчи и джиттер (статус `queued` → `executed`, ожидание до N с) и опцию `instant: true` с пометкой «less private».
13. **`withdraw_token`:** `smart` по умолчанию `{ parts: 1, maxDelayMin: >0, gasDrop: true }`. Массив `to` исполняется отдельными tx с разных vault.
14. **`claim`:** только реестровая операция, on-chain сбор идёт по глобальному расписанию.
15. **`PlatformStats.zecShielded`:** суточная гранулярность, округление (или убрать).
16. **`create.meta.image`:** сервер удаляет метаданные и перекодирует. Клиент шлёт файл только на наш бэкенд, никогда напрямую в IPFS.
17. **`ChatMessage`:** явно «никогда не содержит pubkey/подпись». Ник = `H("unzeen/chat/v1" ‖ pk ‖ mint)[:N]`.
